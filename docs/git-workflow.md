# Git / GitHub 運用ルール

ブランチ運用・Issue ベース開発・PR の詳細ルールを定めます。中核ルールの要約は [CLAUDE.md](../CLAUDE.md) の「Git / GitHub 運用ルール」を参照してください。

> 本ルールは制定以降の作業に適用します。制定前に作成済みのブランチ・PR には遡及しません。

> **ホスティング前提**: 本ガイドは GitHub（`gh` コマンド）を前提に記述しています。GitLab / その他のホスティングを使う場合は、キックオフ時に `gh` 操作・Issue 起票の記述を当該ホスティングのコマンド / 用語へ読み替えてください（ブランチモデル・命名規則・作業フローはそのまま適用できます）。

---

## 1. ブランチモデル

**GitHub Flow** を採用します（`develop` ブランチは使いません）。

- `main` が常にデプロイ可能な唯一の長期ブランチ。
- すべての変更は `main` から切ったフィーチャーブランチで行い、`main` へ PR を出してマージする。
- **`main` で直接コミットしない。**

このルールは二段構えで機械的に強制できる（クライアント側を同梱済み）。

- **クライアント側（早期警告）**: Claude Code の PreToolUse hook（[.claude/hooks/block_main_commit.py](../.claude/hooks/block_main_commit.py)・[.claude/settings.json](../.claude/settings.json)）が、カレントブランチが `main` のときの `git commit` / `git push` をコミット前にブロックする。対象は Claude Code の Bash / PowerShell ツール経由のコマンドのみ（matcher `Bash|PowerShell`）。判定はカレントブランチのみで、git コマンド失敗時等は**フェイルオープン**（誤って全コマンドをブロックしない）。検出は「単発・複合コマンド（`&&` / `;` / `|` 区切り）のサブコマンド位置での `git commit` / `git push` 一致」に留め、`git -c k=v commit` のようなオプション挟み込みや文字列内の擦り抜けは追わない（誤ブロック回避を優先し、擦り抜けはサーバー側に委ねる設計）。**例外としてリモートブランチの削除**（`git push --delete` / `-d` を含む、または**リモート名を除く refspec がすべて `:branch` 形**）は `main` 上でも通す。マージ後のブランチ削除は `main` へ戻ってから行う正規の手順（§5 step 9・`/finish-task`）であり、かつ削除は `main` の履歴を変更しないため、本 hook の目的（main への直接の変更を防ぐ）から外れるため。**削除と通常 push の混在**（`git push origin main :old`）は削除とみなさずブロックする（`main` の履歴を変更する push を擦り抜けさせないため、削除 refspec が 1 つでもあれば通す判定にはしない）。`--force` / `-f` は削除ではないので従来どおりブロックする。settings.json の hook 定義は **exec form**（`command` + `args` 配列・`${CLAUDE_PROJECT_DIR}` プレースホルダは Claude Code が置換）とする（shell form はシェル展開・PATH 解決依存で Windows にて不発火の実績があるため）。hooks はセッション開始時に読み込まれるため、変更後の実効確認は新しいセッションで行う。起動子が動かない場合も Claude Code は非ブロッキング扱いでコマンドを通す（フェイルオープン）が、その状態では hook が無効なので注意。
- **クライアント側（編集時点）**: PreToolUse hook（[.claude/hooks/block_main_edit.py](../.claude/hooks/block_main_edit.py)・matcher `Edit|Write|NotebookEdit`）が、カレントブランチが `main` のときの**リポジトリ内ファイルの編集**をブロックする。commit 時点まで気付かないのを避けるため。対象パスは `tool_input.file_path`（Edit / Write）と `tool_input.notebook_path`（NotebookEdit）の**両方**から解決する（matcher に `NotebookEdit` を入れても `file_path` しか見なければ素通りするため）。**リポジトリ外のパスは対象外**（Claude Code のメモリなど無関係の書き込みを巻き込まない）。パス解決・ブランチ判定に失敗した場合はフェイルオープン（通す）。
- **サーバー側（最後の砦）**: ホスティング側の branch protection で `main` への直 push を管理者を含めて拒否する（GitHub なら branch protection の `enforce_admins` を有効化）。PR 経由のマージには影響しない。緊急時に一時解除した場合は、対応後に必ず再有効化する。

ブランチ判定は hook 入力の `cwd` を起点にした**実効ディレクトリ**に対して行う。複合コマンド内の `cd <path>` セグメントを追跡し、git のグローバルオプション `-C <path>`（空白区切り・複数指定の累積）も解決したうえで、対象リポジトリのカレントブランチを判定する。これにより別リポジトリの feature ブランチへの commit/push は誤ブロックせず、別リポジトリの `main` 上なら従来どおりブロックする。`--git-dir` / `--work-tree` によるリポジトリ指定・クォート付きパス（スペースを含むパス）は追わず、パス解決に失敗するケースは一律フェイルオープン（通す）。

```
main ──┬──────────────────┬──→ (本番)
       │ feature/12-foo    │
       └──────────────────┘ PR → main
```

## 2. GitHub 操作

- 接続・起票・閲覧・PR 作成などの GitHub 操作には必ず `gh` コマンドを使用する。
- PR のベースブランチは常に `main`。
- マージ方式はマージコミット（リポジトリの履歴に合わせる）。**マージはユーザーの承認後に行う。**

## 3. Issue ベース開発

修正・機能追加は Issue の内容に基づいて実施します。

- Claude が Issue を起票する際は、**AI が単独で実装・完結できる粒度**の技術仕様を記述する。最低限、以下を含める。
  - **背景 / 目的**: なぜ必要か
  - **受け入れ条件**: 完了の判定基準（チェックリスト形式が望ましい）
  - **対象ファイル・モジュール**: 変更が想定される箇所
  - **関連ドキュメント**: 該当する `docs/spec/` / `docs/arch/` へのリンク
- Issue 本文・コメントは原則日本語で記述する。ただし**既存の Issue / PR スレッドが日本語以外で書かれている場合は、そのスレッドの言語に合わせる**（[CLAUDE.md 言語ルール](../CLAUDE.md#言語ルール)の「既存スレッドへの追従（例外）」に従う）。Claude が新規起票する場合は日本語をデフォルトとする。

### Issue と `docs/task/` の役割分担

|          | GitHub Issue                       | `docs/task/{slug}.md`                |
| -------- | ---------------------------------- | ------------------------------------ |
| 役割     | 起票・仕様・受け入れ条件の**正本** | 作業中の**設計・進捗メモ**           |
| 主な内容 | 背景・受け入れ条件・対象範囲       | 実装方針・検討メモ・検証結果         |
| 紐付け   | 本文に対応する task ファイルを記載 | 冒頭に対応 Issue 番号 (`#12`) を記載 |

両者は相互リンクで紐付けます。タスクの進捗・完了管理は従来どおり [docs/task/index.md](task/index.md) で行います（[CLAUDE.md タスク管理ルール](../CLAUDE.md#タスク管理ルール)参照）。

> **docs を訂正したら、その記述を引き写している Issue が無いか確かめること。** Issue は起票時の docs を読んで書かれるため、**docs 側の訂正は Issue 本文へ自動では伝播しない**。特に未着手 Issue の「ブランチ運用」「対象ファイル」「着手時に読むもの」は docs の記述を写している率が高く、そこが古いまま残ると**次のタスクが誤った前提で始まる**。確認は `gh issue list --state open` の各本文を、訂正した固有名（ブランチ名・ファイルパス・コミットハッシュ）で grep すれば足りる。

## 4. ブランチ命名規則

| 種別             | 命名                                  | Issue 番号 | 用途                   |
| ---------------- | ------------------------------------- | ---------- | ---------------------- |
| フィーチャー     | `feature/<issue>-<short-description>` | 必須       | 機能追加               |
| バグ修正         | `bugfix/<issue>-<short-description>`  | 必須       | 不具合修正             |
| ホットフィックス | `hotfix/<issue>-<short-description>`  | 必須       | 緊急修正               |
| リファクタリング | `refactor/<short-description>`        | 不要       | 振る舞い不変の内部改善 |
| ドキュメント     | `docs/<short-description>`            | 不要       | ドキュメントのみの変更 |
| 雑務             | `chore/<short-description>`           | 不要       | 依存更新・設定変更など |

- `<short-description>` は内容を表す英小文字 + ハイフン（kebab-case）。例: `feature/12-proxy-settings`。
- `feature` / `bugfix` / `hotfix` は対応する Issue を前提とし、ブランチ名に Issue 番号を含める。
- `refactor` / `docs` / `chore` は Issue を伴わない作業のため番号は付けない。

## 5. 作業フロー（標準）

**docs（設計）先行・テストファースト**を基本とする。設計をドキュメントで固めてから実装に入り、テストは仕様に基づいて先に書く。

1. 対象 Issue を確認（無ければ §3 の要件で起票）。
2. `main` を最新化し、§4 の規則でブランチを作成。
3. docs 先・コード裏取りで調査する（[CLAUDE.md](../CLAUDE.md) の調査ルール）。**調査は読み取り専用の `investigate` サブエージェント（Sonnet）へ委譲し、主エージェントは結論（要点・関連 `path:line`）だけを受け取る**（[CLAUDE.md 調査ルール](../CLAUDE.md#調査ルール-docs-先コード裏取り)参照）。設計・実装方針の判断は委譲せず主エージェントが行う。
   - **step 3.5（受け入れ条件レビュー）**: docs 先行・実装に入る前に、`criteria-review` サブエージェント（Sonnet）で **受け入れ条件・spec そのものの妥当性**（テスト可能・網羅的・非曖昧・意図との整合）を点検する。**助言でありゲートではない**（指摘の採否・条件の修正は主エージェント＋ユーザーが判断、§5.1）。`evaluator`（step 7）が実装の**適合性**を PR 前に独立評価するのに対し、こちらは実装前に**条件自体の妥当性**を見る（対象が逆で補完関係）。安価（Sonnet）で常時運用の助言。`refactor` / `docs` / `chore`（受け入れ条件を持たない作業）は対象外。
4. **設計を `docs/spec/` / `docs/arch/` に先に反映する**（実装前にドキュメントで設計を固める。[docs-guide.md](docs-guide.md) §4 の更新先に従う）。
   - **step 4.5（設計レビュー・条件付き）**: §5.5 の発火条件に該当し、かつ設計レビューモード（§5.2）が有効な場合、docs に固めた設計案を `design-review` サブエージェント（Opus）で点検する（アーキ整合・代替案・結合/スコープ・リスク・docs 整合）。**助言でありゲートではない**（設計方針の最終決定は主エージェント＋ユーザー、§5.1）。発火可否は主エージェントの主観では決めず、investigate（step 3）の「設計レビュー推奨」と §5.5 のトリガで機械的に判定する。推奨が yes のとき主エージェントは自己判断でスキップせず、省略する場合は理由をユーザーに提示して承認を得る。`criteria-review`（step 3.5・条件の妥当性）とは対象が異なり、設計案そのものの妥当性を見る。
5. **テストを先に書く**。テストは spec / 受け入れ条件に基づいて書き、実装に合わせて書かない（[テスト方針](testing/policy.md)）。
6. 実装してテストを green にする。**実装をサブエージェント（`implementer`）へ委譲するときの取り決めと、主エージェント側の義務は §5.2「実装の委譲」**（正本。ここには再掲しない）。
7. **検証ゲート**（PR 前。いずれもサブエージェントへ委譲、§5.2。`/verify-gate` skill でブランチ種別・evaluator モードに応じて一括起動できる、§5.3）:
   - lint / フォーマット / 型チェック / テストを `verify` サブエージェント（Sonnet）で green にする（[CLAUDE.md](../CLAUDE.md) のコマンド参照）。
   - docs / CLAUDE.md を変更した場合は `docs-check` サブエージェント（Sonnet）で整合性（index 更新漏れ・リンク切れ・**旧語彙の残存**・命名・関連仕様リンク）を点検する。
   - `feature` / `bugfix` / `hotfix` ブランチでは `evaluator` サブエージェント（Opus）で受け入れ条件・spec の充足を独立評価する（起動可否は CLAUDE.md の評価ゲートモードに従う、§5.2）。
8. PR を作成（ベース `main`、本文は原則日本語＝対応する Issue スレッドが日本語以外ならその言語に合わせる、関連 Issue を `Closes #<issue>` で紐付け）。GitHub 以外は冒頭注記の読み替えに従う。
   - **`Closes #<issue>` の有無は作成直後に機械的に確認する**（`gh pr view <pr> --json body -q .body | grep -cE '^(Closes|Fixes|Resolves) #[0-9]+'`。行頭に限るのは、本文の説明文やコードスパンに出てくる `Closes #` という文字列に当たって、書き漏らしを「書いてある」と誤判定しないため）。書き漏らすと Issue が open のまま残り、気づくのは後日になる。
   - **PR を出した直後はマージ待ちで止まる**ので通知を出す（§5.8）。
9. **ユーザーの承認後**にマージし、マージ済みブランチを削除。**対応 Issue が open のままなら、受け入れ条件の充足を現在の `main` で裏取りしたうえで close する**（`Closes #` の書き漏らしを拾う安全網。親 Issue・部分完了は close しない）。完了タスクの archive 移動は**原則 step 6〜8 の実装 PR に同梱**する（[docs-guide.md](docs-guide.md) §4.2）。マージ後の後処理（main 最新化・ブランチ削除・対応 Issue の close、同梱できなかった場合のまとめ archive 移動）は `/finish-task` skill で実行できる（§5.3）。

### 5.1 補足ルール

- **設計外の問題への対応**: 実装中に設計段階で考慮していなかった問題が出た場合は、勝手に判断せず**対応案をユーザーに提示して確認を取る**（設計の変更はユーザーの判断事項として扱う）。
- **コミット粒度**: テストを先に書いても、失敗（red）のテスト単独ではコミットしない。実装まで進めて green にしてから 1 コミットにまとめる。

### 5.2 サブエージェントへの委譲

機械的・探索的な作業、および独立評価は専用のサブエージェントへ委譲し、主エージェントの文脈を温存する。定義は `.claude/agents/` 配下。調査・検証・docs 整合・受け入れ条件レビュー・**実装**は Sonnet、独立評価（`evaluator`）と設計レビュー（`design-review`）は Opus を使う。**設計・仕様の判断、テスト内容の決定、設計外の問題への対応は委譲せず、主エージェントとユーザーが行う**（§5.1）。

| エージェント                                              | モデル / effort   | 委譲する作業                                                                                                                                                                                                                  | 対応するフロー | 主エージェントが受け取るもの                                                                                                                 |
| --------------------------------------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| [`investigate`](../.claude/agents/investigate.md)         | Sonnet / `medium` | docs 先・コード裏取りの調査                                                                                                                                                                                                   | step 3         | 結論・関連 `path:line`・裏取りメモ                                                                                                           |
| [`criteria-review`](../.claude/agents/criteria-review.md) | Sonnet / `medium` | 受け入れ条件・spec の妥当性を実装前に点検（助言・常時）                                                                                                                                                                       | step 3.5       | 受け入れ条件の指摘・改善案（採否は委譲しない）                                                                                               |
| [`design-review`](../.claude/agents/design-review.md)     | Opus / `high`     | 設計案の妥当性を実装前に点検（助言・§5.5 発火時）                                                                                                                                                                             | step 4.5       | 設計の指摘・改善案（設計方針の決定は委譲しない）                                                                                             |
| [`implementer`](../.claude/agents/implementer.md)         | Sonnet / `high`   | **設計と受け入れ条件が固まった実装**をブリーフ（ファイル）に従って行い green にする。設計・仕様の判断とテスト内容の決定は委譲しない（下記「実装の委譲」）。commit / push はしない                                             | step 6         | やったこと（`path:line`）・実行したコマンドと exit コード・**検査を外したときの実際の例外 / 出力**・触ったファイルの一覧・判断に迷って戻す点 |
| [`verify`](../.claude/agents/verify.md)                   | Sonnet / `low`    | lint / フォーマット / 型 / テストを green にする                                                                                                                                                                              | step 7         | 検証結果・修正点・要判断項目                                                                                                                 |
| [`docs-check`](../.claude/agents/docs-check.md)           | Sonnet / `low`    | docs 整合性の点検と機械的修正                                                                                                                                                                                                 | step 7         | 点検結果・修正点・要対応項目                                                                                                                 |
| [`evaluator`](../.claude/agents/evaluator.md)             | Opus / `high`     | 受け入れ条件・spec の充足を独立評価。受け入れ条件・タスクメモが限定つきと宣言した主張には、**伝播の一貫性**（同じ事実を書いた全箇所に限定句があるか。事実を指す語で木全体を `git grep` → 各箇所を読む）も判定する（評価軸 6） | step 7         | 総合判定（区分つき）・受け入れ条件ごとの合否・要対応項目                                                                                     |

#### 実装の委譲

**実装を `implementer`（Sonnet / `high`）へ委譲するときの取り決めと、主エージェント側の義務。本節が正本**で、`start-task`（§5.3）と [`implementer.md`](../.claude/agents/implementer.md) はここを指し、規則を再掲しない。

**いつ委譲するか / しないか**

- 委譲してよい: **対象ファイルが列挙でき、判定・期待値が設計として固まっている**段階（step 6）。
- 委譲しない: 設計が未確定・対象が読むまで決まらないもの、**設計や仕様の判断そのもの**、テスト内容（ケース表・期待値）の決定。これらは §5.2 冒頭の「委譲しない」に含まれる。小さい実装は委譲せず主エージェントが書いてよい。

**ブリーフの渡し方**

- **ブリーフは `.brief/` のファイルで渡し、起動プロンプトにはパスと「このファイルを読め・文脈を失ったと感じたら読み直せ」だけを書く。** prompt に書いた禁止事項は auto-compact で消えるが、ファイルは読み直せる（膨張の主因は tool 出力なので、prompt を短くするだけでは効かない）。雛形は [`implementer-brief-template.md`](../.claude/skills/start-task/implementer-brief-template.md)。
- **`.brief/` は `.gitignore` 済みで、追跡もされない。** **scratchpad には置かない** — セッション固有なので `/clear` した瞬間に消える。
- **差し戻し・追加指示はブリーフ末尾の追記節へ書く。** サブエージェントへのメッセージ本文だけで送ると、同じ理由で消える。
- **触ってよいファイルを明示する。** 並行させるときは「**相手が同じ木で作業している**」の 1 行を各ブリーフに入れる。

**主エージェントの義務**（実装担当の報告を信用して省略しない）

1. **検証は自分で回し直す。** 実装担当の報告を検証の証跡にしない。**境界**: `verify` の報告は証跡として採ってよい（実装していない）が、`implementer` の報告は採らない。
2. **対応表は件数ではなく行単位で突き合わせる**（件数の一致の裏に偽 green を生む欠陥が隠れる）。
3. **「検査を外したときの結果」は実際の例外・出力で読む。** assert の文面で読まない（別の例外で落ちていたのを「狙った検査で red」と読み違える）。実装担当の報告フォーマットの当該欄を見る。
4. **分割したら、境界をまたぐ引用を洗う。** 各ブリーフが書き換えた正本の**固有名**（節番号・記号・既定値）で他のブリーフの守備範囲を `git grep` し、**当たった行を 1 件ずつ読んで**旧値のままか新値に揃っているかを判定する（評価軸 6 と同じ強さ。grep の件数で終えない）。**ブリーフの分割線がそのままドリフトの線になる**。
5. **「入っている・直った」という報告は、存在の確認で終えず、発火順序・適用条件まで確かめる。**

**effort をエージェント側で固定する理由**: 指定しないとセッションの effort をそのまま継承するため、**同じエージェントの判定力がその日の設定で変わる**。特に `evaluator` / `design-review` は「レビュアーが生成者より弱いと追認してしまう」という理由で上位モデルを割り当てているのに、effort がセッション任せだとその前提が崩れる。逆に `verify` / `docs-check` は結果を客観的に検証できる機械的作業なので、最も頻度が高いにもかかわらず高い effort を継承するのは無駄。**モデル（能力の器）と effort（考える深さ）を別々に固定**し、どちらもセッション設定に依存させない。より厳しく見たい回はユーザーが起動時にオーバーライドしてよい（`design-review` / `evaluator` を `xhigh` に上げる等）。

読み取り専任のエージェント（`investigate` / `criteria-review` / `design-review` / `evaluator`）は、`tools` から `Edit` / `Write` を外すだけでは `Bash` 経由の書き込み・commit を防げない。そこで frontmatter に **`permissionMode: plan`（読み取り専用モード）** を指定し、本文の約束ではなく機構で担保する。特に `evaluator` の独立性は本 harness の中核であり、口約束に委ねない。ただし親セッションが `bypassPermissions` / `acceptEdits` / auto モードの場合は親の権限モードが優先されエージェント側の指定は無視されるため、各エージェント本文の「読み取り専用」の記述も残す（二段構え）。`verify` / `docs-check` / `implementer` は書き込みを行うため対象外で、`implementer` が commit / push をしない約束は本文だけで担保する（「実装の委譲」）。

調査・検証・docs 整合・実装の委譲は費用対効果で判断してよい（一発で通る見込みなら `verify` を介さず直接回す、軽い確認は `investigate` を介さず直接読む、小さい実装は `implementer` を介さず自分で書く等）。`evaluator` と `design-review` が Opus なのは、他の Sonnet 勢が結果を客観的に検証できる機械的・構造的タスクなのに対し、この 2 つは裁量を伴う判断だから。生成側（主エージェント）も上位モデルのため、評価者・レビュアーが弱いと、`evaluator` では実装の見落としを、`design-review` では不十分な設計を、それぞれ追認してしまう。

`criteria-review` は `evaluator` と対をなすが**性格が逆**で、実装前に受け入れ条件**自体**の妥当性を点検する**助言**であり、ゲート化しない（通過可否・条件の修正は主エージェント＋ユーザーが判断、§5.1）。安価（Sonnet）で価値が高いため常時運用の助言とし、モードは設けない。`design-review` も助言だが、設計批評そのものが高裁量のため Opus とし、§5.5 の発火条件＋設計レビューモードに該当する時だけ起動する。

#### 評価ゲート（evaluator）のモード

`evaluator` の起動可否は **CLAUDE.md の「評価ゲート（evaluator）モード」** を単一の正本として決める（`/verify-gate` skill はこの値を読むだけ）。対象は受け入れ条件を持つ `feature` / `bugfix` / `hotfix` ブランチのみで、`refactor` / `docs` / `chore` は常に対象外。

| モード   | 挙動                                                                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `always` | 対象ブランチで**必ず**起動（省略不可）。「単純だから不要」という判断自体が、evaluator で排除したい自己評価バイアスに当たるため、起動可否を裁量に委ねない                                                     |
| `auto`   | 変更規模が**閾値**を超える回に自動起動する。評価後に **1 度だけ**「以降 `always` に固定するか」を確認し、Yes なら CLAUDE.md のモードを `always` へ更新（昇格は一方向・固定）。閾値以下の回はスキップしてよい |
| `off`    | 起動しない。`.claude/agents/evaluator.md` は同梱済みのため、いつでも `auto` / `always` へ昇格できる                                                                                                          |

**auto の発火閾値**（いずれかを満たせば「大きい変更」とみなす。数値はプロジェクトに合わせて調整可）:

- 変更ファイル数 ≧ 5、**または**
- 変更行数（追加 + 削除）≧ 200、**または**
- `docs/spec/` 配下の新規 spec ファイルを含む。

> モードは思想的には `always` が正統（バイアス排除の観点）。`auto` / `off` は立ち上げ初期の負荷を下げる割り切りで、プロジェクトが成熟したら `always` へ上げることを想定している。雛形の初期値は `auto`。

#### 評価ゲートの指摘区分と止め時

モードが `always` でも、**何巡で止めるか**の規則が無いと、後半の巡回は「証跡の鮮度」「記述の網羅性」のように**正しいが PR を止める必要のない指摘**で占められ、上位モデルの再評価が費用だけ消費する。本節を**指摘の区分と止め時の正本**とする（`evaluator` の報告形式・`/verify-gate` の集約はここを読むだけで、規則を再定義しない）。**モードは変えない** — 変えるのは起動可否ではなく巡回の終わり方である。

**「巡」= `evaluator` サブエージェントの 1 回の起動。** 間に挟まる `verify` / `docs-check` の往復は数えない。

**区分は 2 つ。判定基準は「閉じるのに何を変える必要があるか」**（指摘の話題ではなく**所在**で分ける）。**所在は、指摘を提起された形のまま正直に閉じられる最小の変更で決める** — あとで是正として選んだ道（docs で閉じられた指摘をコードの拡張で閉じた等）では決めない。「spec」は `docs/spec/` に限らず、その振る舞いの正本と宣言された文書を含む。

| 区分           | 定義                                                                                                                                                                                                                                                                                                                                                                          | PR への効き方                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **欠陥**       | 閉じるのに**コード・ゲートの出力・検査スクリプト・spec** の変更が要る指摘。受け入れ条件の未充足、機能が動かない、**検査が偽 PASS / 偽 FAIL を出しうる**、spec と実装の乖離、既存の検査で殺せない変異（検出力の穴）、[policy §8.1 A1](testing/policy.md) の変異 → red の証跡を**そのタスクで一度も示していない**（または示すための検査が無い）、潜在バグ（今は偶然通っている） | **ブロックする**。直して再評価                                                                                                                   |
| **証跡・文言** | **docs・タスクメモ・コメントの編集**（既存の検査の再実行と貼り直しを含む）だけで閉じる指摘。主張が実測を上回る**記述**、記述の網羅性、証跡の**鮮度**（採取後にコードが変わった）、行番号・名前の腐り、docs・報告文中のラベルの分かりにくさ（**検査スクリプトが出力するラベルは「ゲートの出力」側 = 欠陥**）                                                                   | **ブロックしない**。同じ PR で直すか、follow-up Issue に落として PR を進める。**どちらにしたかを報告に書く**（Issue を作らず握りつぶすのは不可） |

> **「実測を上回る主張」は所在で分かれる。** メモや docs の記述なら証跡・文言。**ゲートの出力**に現れるもの（例: 判定は「不明」なのに注意行が秒数を断定する）は**出力の欠陥**であり、[policy §8.2](testing/policy.md) が測定器の型として扱うのはこちら。
>
> **証跡の「無い」と「古い」は、タスク単位・検査単位で分ける**（変異 1 件ごとではない）。**無い** = そのタスクで変異 → red を一度も示していない、または示すための検査が無い → 欠陥（閉じるには検査を書くか回す必要がある）。**古い** = 示したあとにコードが動き、貼ってある証跡が最終状態と違う → 証跡・文言（**既存の検査の再実行と貼り直し**で閉じる）。

**止め時の規則**

1. `evaluator` は**要対応の各項目に区分を付けて**報告する（区分の割り当て主体は evaluator。主エージェントは「証跡・文言」を「欠陥」へ**格上げしてよいが、格下げはできない** — 格下げを許すと、evaluator が排除している自己評価バイアスの抜け道になる）。総合判定は 3 値: **PASS** / **PASS（follow-up あり）** / **FAIL**（欠陥が 1 件でもあれば FAIL）。
2. **欠陥が 0 件なら、その巡で PASS 扱い**にして PR へ進む（1 巡目を含む — 証跡・文言しか無い回に上位モデルの再評価をもう 1 回回す理由が無い）。残った証跡・文言は同じ PR で直すか follow-up Issue に落とす。**証跡・文言だけを直したあとの再評価は要らない**（再評価が要るのは欠陥を直したときだけ）。
3. 欠陥が残る巡は直して再評価する。巡数の上限は置かない（欠陥を残したまま通す規則は作らない）。**再評価の起動プロンプトには前回の報告を引き継ぐ**: 前回の要対応項目を**区分ごとに全部**（指摘文・`path:line`）と、各項目の**閉じ方の種別**（コード修正 / 証跡の再取得 / 条件改訂）と**証跡パスまたはコミット**を表にして渡し、「ここから確認を始める」と指示する。**同じ表をタスクメモにも残す**（後から辿れる形）。渡さないと再評価が毎回ゼロから始まり、閉じた項目の再導出に巡が費やされる。

**follow-up Issue に書くもの**（最低限）: 元 Issue / PR 番号、指摘があった evaluator の巡と評価軸、`path:line`、指摘の文面。起票したら [docs/task/index.md](task/index.md) の「起票済み・未着手の Issue」表に載せ、PR 本文の `Closes #<issue>` と並べて **`Follow-up: #<N>`** を書く（`gh pr view <pr> --json body -q .body | grep -cE '^Follow-up: #[0-9]+'` で機械確認できる形。行頭に限る理由は §5 step 8 の `Closes #` 確認と同じ — 本文の説明文やコードスパンに出てくる `Follow-up: #` に当たって、書き漏らしを「書いてある」と誤判定しないため。`Follow-up: #<N>` は字下げや箇条書き記号を付けずに行頭から書く）。

#### 設計レビュー（design-review）のモード

`design-review`（step 4.5）の起動可否も **CLAUDE.md の「設計レビュー（design-review）モード」** を単一の正本として決める。evaluator と違い実装前・助言・高コスト（Opus）なので、既定は §5.5 の構造トリガに従う `auto`。

| モード   | 挙動                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `always` | 規模・トリガに関わらず、設計を伴うタスク（docs 先行で設計を固めた回）で毎回起動する                                                                |
| `auto`   | **§5.5 の発火トリガに該当する回だけ**起動する（investigate の「設計レビュー推奨」が yes の時）。設計余地の大きい変更を守りつつ、単純タスクでは省く |
| `off`    | 起動しない。`.claude/agents/design-review.md` は同梱済みのため、いつでも `auto` / `always` へ昇格できる                                            |

> evaluator の `auto` が「変更規模のしきい値」で発火するのに対し、design-review の `auto` は **§5.5 の構造トリガ**（新モジュール・新しい境界・複数モジュール横断など）で発火する。設計の複雑さは diff の大きさと相関しないため、判定軸を分けている。雛形の初期値は `auto`。

### 5.3 スキル（オーケストレーション入口）

定型の多段手順は `.claude/skills/` 配下の skill にまとめ、`/<skill 名>` で起動する。skill は**手順の入口**であり、起動条件・モデル選定・evaluator モードなどの**ルールは再定義せず §5.2 等の正本を参照**する（二重管理＝drift を避けるため）。

| skill                                                       | 役割                                                                                                                                                                                                                                                                                              | 対応するフロー                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| [`start-task`](../.claude/skills/start-task/SKILL.md)       | Issue 確認/起票・ブランチ作成・`investigate` 起動・`criteria-review`（受け入れ条件レビュー・助言）・（§5.5 発火時）`design-review`（設計レビュー・助言）・docs 先/テスト先の順序ゲート（判断は自動化せず確認に留める）・実装（自分で書くか `implementer` へ委譲するかの分岐。§5.2「実装の委譲」） | step 1〜6                                      |
| [`verify-gate`](../.claude/skills/verify-gate/SKILL.md)     | ブランチ種別を判定し `verify` →（docs 変更時）`docs-check` →（feature/bugfix/hotfix・モードに応じて）`evaluator` を順に起動・集約                                                                                                                                                                 | step 7                                         |
| [`finish-task`](../.claude/skills/finish-task/SKILL.md)     | `main` 最新化・マージ済みブランチ削除・**対応 Issue の close**（`Closes #` の書き漏らしを拾う安全網）・（実装 PR に同梱できなかった場合の補完として）完了タスクの archive 移動（複数タスクまとめ可・docs ブランチ＋PR）                                                                           | step 9                                         |
| [`harness-retro`](../.claude/skills/harness-retro/SKILL.md) | ハーネス見直し。`extract` で窓内の archive・コミットと全メモリから候補を抜き出し、実害の実例・置き場所・配分つきの候補表をユーザーに示して選ばれたものを起票・記録する。`cleanup` でメモリを縮める・畳む・統合し、消した名前を先に記録する                                                        | §5.9（**標準フロー外**・ユーザーが求めたとき） |

skill が呼ぶサブエージェントの**合否・設計判断は委譲しない**点は §5.1 / §5.2 と同じ。skill は正しい順序・条件での起動と結果集約に徹する。ホスト操作（Issue / PR）を含む skill は冒頭注記の読み替えに従う。

**`allowed-tools` は起動ターン中の事前承認（frontmatter には置かない）**: 列挙したツールをそのターンに確認なしで使える grant であり、他のツールの利用可能性は制限しない。次のユーザーメッセージで grant は解除される（公式確認: 2026-09-14、[Pre-approve tools for a skill](https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill)）。

**承認の省略は `permissions.allow` に一本化する**（§5.6）。ユーザーの返答をまたぐ skill では grant の有効期間が切れるため、skill には権限を付けない。常時許可してよいコマンドだけを allow へ登録する。

| skill           | 承認の扱い                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `start-task`    | `git checkout main` / `git pull --ff-only` / `git checkout -b` は §5.6 の allow に登録。**`gh issue create`** は都度確認 — Issue を外部に立てる操作は内容の確認を挟む                                                                                                                                                                                                                                                                                                                                                                             |
| `finish-task`   | `git branch -d` / `git fetch --prune` / `gh pr list` / `gh pr view` / `gh issue view`（参照系。手順 B-1 で毎回走る）は allow に登録。**手順 B-1 の `gh api graphql`（PR が閉じる Issue の取得）は都度確認**（§5.6 の「allow に入れない」。B-1 は毎回 1 度確認を挟む）。**`gh issue close` は都度確認**（Issue を閉じる操作は根拠コメントの確認を挟む）。**`git push origin --delete` は allow に入れない**（§5.6 の「`git commit` / `git push` は都度確認」を後退させないため）。手順 C の `git commit` / `git push`（archive 移動 PR）も都度確認 |
| `verify-gate`   | 追加なし（使う git が `status` / `diff` / `branch --show-current` の参照系のみで元々承認不要）                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `harness-retro` | 追加なし。**`gh issue create`・記録の `git commit` / `git push` は都度確認**。メモリの削除・統合は権限の話ではなく手順の確認で、`AskUserQuestion` で可否を取る（§5.9。メモリは repo の外にあり allow / deny も hook も効かない）                                                                                                                                                                                                                                                                                                                  |

### 5.4 ルール層（path-scoped、`.claude/rules/`）

特定の種類のファイルを編集する瞬間にだけ思い出すべき遵守事項は、`.claude/rules/` 配下に **path-scoped rule** として置く。Claude Code はマッチするファイルを読んだ時にそのルールをコンテキストへ自動注入する（`paths` frontmatter の glob で対象を指定）。CLAUDE.md（常時ロード）と違い、関係するファイルを触る時だけ載るため文脈を節約できる。

- **薄いポインタに徹し、正本は再定義しない**: ルール本文に手順をコピーすると単一情報源が崩れる（§5.3 の skill と同じく、判断・正本は一箇所に集約する）。各 rule は対応する正本 docs を指し、編集時に外しやすい要点だけを再掲する。
- **順序ゲートの置き換えではなく補完**: path-scoped は「マッチするファイルを _読んだ_ 後」に発火するため、新規領域では発火が遅れることがある。docs 先・テスト先（§5 step4-5）や PR 前の検証ゲート（§5 step7）を代替しない。

雛形には以下を同梱している（`paths` の glob はキックオフでプロジェクトのテスト配置に合わせて置換する）。

| rule                                                | `paths`                                   | 正本                                   | 効かせたい瞬間                                                                    |
| --------------------------------------------------- | ----------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------- |
| [`testing.md`](../.claude/rules/testing.md)         | テストファイルの glob（キックオフで置換） | [testing/policy.md](testing/policy.md) | テストを書く / 直す時（テストファースト・red 単独コミット禁止）                   |
| [`docs-upkeep.md`](../.claude/rules/docs-upkeep.md) | `docs/*.md`, `docs/**/*.md`               | [docs-guide.md](docs-guide.md)         | spec / arch / task を編集する時（index 追記・相互リンク・archive 手順の漏れ防止） |

### 5.5 設計レビュー（`design-review`）の発火条件

設計レビュー（step 4.5）は全タスクには回さない。単純タスクではノイズ・コストが過剰になる一方、「単純だから省く」を主エージェントの主観に委ねると `evaluator` を必須化したのと同じ自己評価バイアス（「不要」という判断自体がバイアス）に陥る。そこで**発火は客観的な構造トリガで機械的に判定**し、主エージェントの主観に委ねない（設計レビューモードが `auto` のときの発火条件。`always` は常に、`off` は起動しない。§5.2）。

**発火トリガ（いずれか 1 つでも該当 → 実施を既定とする）**

| トリガ                                                                                       | 理由（設計接続点が増える＝レビュー価値が高い）                                                                            |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 新モジュール追加（対応する `arch/` 新規が必要）                                              | 新しい構造の導入                                                                                                          |
| 新画面・ダイアログ（`spec/screens/` 追加）                                                   | UI 設計の分岐                                                                                                             |
| 新しい並行 / スレッド境界・IO / 永続化層・外部プロセス連携・外部依存の追加                   | アーキ接続点の増加（CLAUDE.md の横断的な実装ルールに関わる）                                                              |
| 複数モジュールにまたがる変更                                                                 | 境界設計の判断が発生                                                                                                      |
| investigate が「実装方針の候補が複数ある / docs が薄く前例なし」と報告                       | 設計余地が大きい                                                                                                          |
| Issue に `needs-design` ラベル or「設計判断」節がある                                        | ユーザーの明示                                                                                                            |
| 外部サービスの API 契約に自前クライアントで直接依存する                                      | 契約は上流都合で予告なく壊れる（PoC の成功はその時点の契約しか保証しない）。公式クライアント・既製手段との比較が必要      |
| 失敗すると自己修復できない機能（自己更新・データマイグレーション・設定スキーマ変更等）       | 不具合修正の配布・復旧経路自体が壊れるため要求信頼性が桁違いに高い                                                        |
| 権限・実行環境差に敏感な操作（symlink / ACL / 保護パス / 昇格前提の API 等）を含む依存・実装 | 開発環境（昇格・特定 OS）での検証が偽陰性になりやすい。[testing/policy.md](testing/policy.md) §7 の環境差検証が必要になる |

**非発火例（省略してよい）**: 設定値 1 個の追加・文言のみ・既存パターンに乗るだけの機能追加・局所的な bugfix・`refactor`（振る舞い不変で既存構造内）。

下 3 つのトリガ（実運用プロジェクトでの検出漏れ実績から一般化した失敗クラス）に該当する設計では、design-review への依頼時に**既製手段（公式 CLI・公式ライブラリの高レベル API・パッケージマネージャ配布等）を代替案として必ず比較対象に含める**こと。自前実装は「外部契約の追従責任」と「全ユーザー環境での動作責任」を自分で負うことを意味し、その妥当性自体が設計判断となる。

**判定ルール**

- トリガ判定は investigate（step 3）が担い、報告に「設計レビュー推奨: yes/no ＋理由」を出す（主エージェントの自己申告に依存させない）。
- モードが `auto` で 1 つでも該当（推奨 yes）→ **実施を既定**とする。主エージェントは主観でスキップせず、省略する場合は**理由をユーザーに提示して承認を得る**（提示のみの自己判断スキップは禁止）。
- ユーザーはオン / オフ両方向でオーバーライドできる（推奨 no でも設計に不安があれば起動を要求してよい。最終判断はユーザー）。
- `design-review` は助言でありゲートではない。指摘の採否・設計方針の最終決定は主エージェント＋ユーザーが行う（§5.1）。

### 5.6 権限ルール（`.claude/settings.json` の `permissions`）

検証ゲート（§5 step 7）で毎回走る品質コマンドは、`permissions.allow` に列挙して都度確認を省く。`verify` が lint / 型 / テストの往復のたびに承認待ちで止まると、委譲の利点（主エージェントの文脈温存）が失われるため。

**allow に入れる**: [CLAUDE.md](../CLAUDE.md) の「Lint / Format / 型チェック」「テスト」節に載っている**読み取り・検証系のコマンド**（`npm run lint` / `lint:fix` / `format` / `format:check` / `typecheck` / `npm test`）と、`gh` の**参照系**（`gh issue view` / `gh issue list` / `gh pr view` / `gh pr list`）。加えて `start-task` / `finish-task` の定型 git 操作のうち**履歴を変更せず取り消しが容易なもの**（`git checkout main` / `git pull --ff-only` / `git checkout -b` / `git branch -d` / `git fetch --prune`）。Claude Code の Bash / PowerShell **両ツール分**を登録する（サブエージェントは Bash を使う一方、主エージェントは Windows では PowerShell を使うため）。テストの入口（`npm test`）を allow に入れておくのは、実装を `implementer` へ委譲するたびに承認待ちにならないためでもある（§5.8 の「ユーザーは画面を見ていない」前提と衝突するため）。

**allow に入れない**（都度確認させる）:

| 対象                                                                    | 理由                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 依存のインストール・更新（`npm install` / `npm ci` 等）                 | 依存ツリーを書き換える                                                                                                                                                                                                                                                         |
| アプリ / サービスの起動・E2E・ビルド（`npm run dev` / `npm run build`） | 重い副作用（プロセス起動・成果物生成）を伴う。実行は主エージェントが明示的に行う（[testing/policy.md](testing/policy.md)）。`npm run build` は CI の検証ゲートに含むが、ローカルでの実行は都度確認とする                                                                       |
| `gh api graphql`（`finish-task` 手順 B-1 などの参照クエリを含む）       | query も mutation も同じコマンドで実行でき、allow の glob では参照だけに絞れないため、参照系（`gh issue view` 等）と同じ扱いにしない。gh 2.45 では `gh pr view --json` に `closingIssuesReferences` が無く B-1 は GraphQL が必要なので、B-1 は毎回確認を挟む運用とする（#300） |
| `git commit` / `git push`                                               | main 判定 hook（§1）とサーバー側 protection の判断を素通りさせない。`finish-task` が使う `git push origin --delete`（リモートブランチ削除）も**例外にしない**（hook は通すが、常時無条件の許可までは与えない）                                                                 |

**deny**: `git push --force` / `-f`（両ツール分）。deny は allow より先に評価され例外を作れないため、広い deny（`git push *` 等）は置かない。

ルールの書式は Bash / PowerShell とも glob で、末尾 ` *` は語境界付きの前方一致（引数なしの実行にもマッチする）。追加・変更時は**この表の分類（検証系は allow、副作用のあるものは都度確認）に沿っているか**を判断基準にする。

### 5.7 hooks 層（`.claude/hooks/`）

**プロンプトの指示に頼らず機構で効かせたいもの**は hook にする。CLAUDE.md に書いた約束はモデルが読み飛ばしうるが、hook は必ず走る。同梱している hook は以下（いずれも標準ライブラリのみ・言語非依存。起動子は `python3`）。雛形は Python 3.10+ 前提だが、本リポジトリの実行環境の `python3` は 3.9 のため、各 hook に `from __future__ import annotations` を足して PEP 604（`X | None`）の注釈を遅延評価にしている（これが無いと import 時に `TypeError` で落ち、フェイルオープン設計ゆえに**何も起きないまま素通り**する）。

| hook                                                                | イベント / matcher                         | 役割                                                                                                                                                                                                                                                                                                                                                                                                       | 正本                                                       |
| ------------------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| [`session_task_status.py`](../.claude/hooks/session_task_status.py) | `SessionStart`                             | [task/index.md](task/index.md) の 2 つの表を `additionalContext` で注入する                                                                                                                                                                                                                                                                                                                                | [CLAUDE.md](../CLAUDE.md) タスク管理ルール                 |
| [`block_main_commit.py`](../.claude/hooks/block_main_commit.py)     | `PreToolUse` / `Bash\|PowerShell`          | `main` 上の `git commit` / `git push` をブロック（ブランチ削除は除く）                                                                                                                                                                                                                                                                                                                                     | §1                                                         |
| [`block_main_edit.py`](../.claude/hooks/block_main_edit.py)         | `PreToolUse` / `Edit\|Write\|NotebookEdit` | `main` 上のリポジトリ内ファイルの編集をブロック                                                                                                                                                                                                                                                                                                                                                            | §1                                                         |
| [`format_edited_file.py`](../.claude/hooks/format_edited_file.py)   | `PostToolUse` / `Edit\|Write`              | 編集したファイルを整形する。対象は**フォーマット（check）コマンドと同じ範囲**にする（本リポジトリは `format:check` が `prettier --check .` なので、`["."]` と空の拡張子集合で全ファイルを `npx prettier --write --ignore-unknown` に渡し、ignore・担当外の判定は Prettier に任せる）。リポジトリ外は対象にせず、cwd はリポジトリのルート（Prettier は `.gitignore` / `.prettierignore` を cwd 基準で探す） | [CLAUDE.md](../CLAUDE.md) の「Lint / Format / 型チェック」 |

共通の設計方針:

- **フェイルオープン**: 判定に迷うケース（パース失敗・パス解決不能・git やツールの失敗）は必ず「通す」に倒す。**想定外の形の入力**（トップレベルが dict でない JSON、`tool_input` が dict でない等）も例外を投げずに**無出力 exit 0** で通す。hook の不調で作業が止まる方が損失が大きい。ブロック系はサーバー側 protection（§1）が最後の砦。
- **正本を再定義しない**: hook は判定と注入に徹し、ルール本文は docs 側に置く（§5.3 の skill・§5.4 の rule と同じ方針）。
- **反映タイミング**: hooks の登録（settings.json）はセッション開始時に読み込まれるため、変更後の実効確認は新しいセッションで行う。hook スクリプト本体は実行のたびに読まれるため即座に効く。
- **検証はスモークで行う**: hook は「効いているつもりで効いていない」状態になっても気付きにくい（matcher に登録済みでも入力キー違いで素通りする、等）。`python3 scripts/smoke_hooks.py` で hook に stdin JSON を直接与え、ブロック / 通過の分岐を確認する（`main` を指す一時 worktree を自動で作る。テスト基盤に依存せず単体で走る）。**hook を変更したら必ず実行すること**。
- **stdin の BOM に注意**: PowerShell のパイプ（`'{...}' | python hook.py`）は stdin に UTF-8 BOM を付けるため、hook が JSON パースに失敗して**フェイルオープンする**（＝何も起きず、成功と見分けがつかない）。手でスモークする場合は BOM なしのファイルをリダイレクトする（Claude Code 本体は BOM を付けないため実運用には影響しない）。

### 5.8 ユーザーへ手を戻すときの通知

**ユーザーは常に Claude Code の画面を見ているわけではない。** 長いビルド・テスト・バッチ実行を挟む作業では、**判断を仰いだまま何十分も止まる**ことが起きる。**本節が通知の運用の正本**で、skill 側（§5.3）は該当箇所に **`**【通知】**`** の印とここへのリンクだけを置き、ルール本文を再掲しない。

#### 出す / 出さない

**発火条件は箇所の一覧ではなく事象で決める** — **ユーザーの返答・操作が無いと次へ進めない状態になったとき**。下の一覧は skill 本文と照合した該当箇所であって、**上限ではない**（新しい手戻り点が増えたら同じ規則が当たる）。

| 出す                                               | 出さない                    |
| -------------------------------------------------- | --------------------------- |
| `AskUserQuestion` を呼ぶとき                       | 進捗報告                    |
| 設計の分岐でユーザー判断を仰ぐとき                 | ゲートが green になっただけ |
| **PR を出してマージ待ちになったとき**（§5 step 8） | 答えの要らない情報提供      |
| 長い待ちのあとに判断が要る結果が出たとき           | —                           |

> **線引きは「作業時間の長短」ではない。** `PushNotification` は**ユーザーが端末に居れば送られず**、結果は "not sent" になる（これは**正常**であって失敗ではない）。「直前に話しかけている」「数秒で終わる」は**ツール側が既に吸収する**。規約が決めるべきなのは**ツールに判別できない軸** — その通知に**返してほしい判断があるか**である。**判断を求めない通知は、注意を安く消費して次の通知の価値を下げる。**

#### 書き方

- **1 行・200 字未満・markdown なし。** モバイルは途中で切れる。
- **「何を決めてほしいか」を先頭に置く。** 「作業完了」ではなく「判定粒度を A と B のどちらにするか」。
- **`status: "proactive"` が要る**（ツールの必須引数。省くと呼び出しが通らない）。
- **通知は入口であって、チャット本文の置き換えではない。** 根拠・選択肢・比較は従来どおりチャットに全文を書く。

#### skill 側の該当箇所

> **「手順 N」は skill 本文の中の番号**であって本ファイルの節番号ではない。

| skill                                                       | 箇所                                                                                                                                                                                                                            |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`start-task`](../.claude/skills/start-task/SKILL.md)       | 手順 1（受け入れ条件をユーザーと確認）・手順 3.5（`criteria-review` の指摘の採否）・手順 4（docs 先行の確認ゲート）・手順 4.5（`design-review` の省略判断）・手順 5（テスト先行の確認ゲート）・「やらないこと」（設計外の問題） |
| [`verify-gate`](../.claude/skills/verify-gate/SKILL.md)     | 手順 2（`verify` に設計判断が要る失敗が残ったとき）・手順 4（`auto` からの昇格確認 / モード行が見つからないとき）・手順 5（`verify` / `docs-check` の FAIL、`evaluator` に `[欠陥]` が残るとき）                                |
| [`finish-task`](../.claude/skills/finish-task/SKILL.md)     | 手順 B-2（親 Issue / 部分完了の close 判断）・手順 C-7（archive PR のマージ待ち）・「やらないこと」（archive テーマ表に区分が無い場合）                                                                                         |
| [`harness-retro`](../.claude/skills/harness-retro/SKILL.md) | extract 手順 4（候補表と起票本数・起票順）・手順 7（記録 PR のマージ待ち）、cleanup 手順 3（処置ごとの可否）・手順 6（記録 PR のマージ待ち）                                                                                    |
| 共通                                                        | **§5 step 8（PR を作った直後）** — 4 つの skill のどれにも属さない                                                                                                                                                              |

> **`.claude/rules/` には置かない。** rule は path-scoped で「そのファイルを**読んだ**とき」に発火するが、通知が要るのは skill の実行中で、**発火のタイミングが合わない**（§5.4 が自ら「順序ゲートの置き換えではなく補完」と書いている）。

### 5.9 ハーネス見直しとメモリ整理

**繰り返した失敗を、窓を切って集め、実害の実例があるものだけを Issue にして機械検査・手順へ落とす。** 落とし終えたら、正本が repo 側にできた分だけメモリを縮める。入口は [`/harness-retro`](../.claude/skills/harness-retro/SKILL.md)（`extract` = 候補の抽出と起票 / `cleanup` = メモリ整理）で、**本節がルールの正本**（抜き出しのコマンドは手順なので skill 側に置く）。1 回ごとの窓・候補表・採否・メモリの前後は [harness-retro-log.md](harness-retro-log.md) に残す。候補表を残さずに Issue の本文だけを成果物にすると、見送った候補とその理由、メモリ整理で消したファイル名が「記録なし」になる — 記録ファイルはその穴を塞ぐためにある。

**いつ回すか**: ユーザーが求めたとき。自分から回し始めない（ハーネス作業は本業 — プロキシ本体のコード — を直接は進めない。下の「ユーザー判断と偏重の歯止め」）。**標準フロー（§5）の外**にある。1 回の見直しは **PR 2 本**になる — `extract` の記録（候補表・起票した Issue を未着手 Issue 表へ）と、`cleanup` の記録。どちらも `docs/` ブランチ（§4）。

#### 窓

- **始点 = 前回の記録の終点**（記録ファイルで「窓:」の行を持つ節のうち、いちばん上の節の終点。メモリ整理だけの節は窓を持たないので数えない）。**終点 = 今回 `extract` で候補を抜き出した時点の `origin/main` の HEAD**（`git fetch` の後に取る。日付とコミットを記録に書く）。**始点のコミット自身の変更は窓に入らない**（`START..END` は始点を含まない）— 初回に「あるタスクから」と決めるなら、そのマージコミットではなく直前のコミットを始点にする。**起票したバッチ自体のタスクは次の窓に入る**。
- **窓で絞るのは archive・コミットの情報源だけ。** メモリには窓を掛けず毎回全体を読む。**実害の実例は窓の外でもよい**（前の窓で完了したタスクを実害に挙げてよい）。
- **窓内の archive 行** = 終点の `docs/task/archive/index.md` にあって始点に無いタスク（**タスクのファイル名で比べる**。完了日の列では切らない — 同日の行が前回と重なり、日付はタイムゾーンで揺れる。`git diff` の `+` 行でも切らない — 既存の行の編集も拾う）。

#### 情報源

| 情報源                                                                                        | 何を拾うか                                               | 形の注意                                                                                                               |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| メモリ（ハーネスがシステムプロンプトで渡す場所）                                              | 癖の型・「何回目か」の数・`feedback` の Why              | 窓を掛けない（上記）。**記録ファイルにメモリの本文を写さない**（ファイル名だけ。実害の実例は Issue・コミットで挙げる） |
| `docs/task/archive/index.md` の窓内の行と、「完了タスクの経緯・申し送り」節に窓内で足された行 | 要判断・経緯・申し送り・follow-up 候補・evaluator の巡数 | 形は揃っていないので概要の散文から拾う                                                                                 |
| 窓内の archive メモ                                                                           | 訂正・手戻りの記述（`## 訂正ログ` 表があればその行）     | 形は揃っていないので本文を読む                                                                                         |
| 窓内の `git log`                                                                              | 訂正コミット（件名に「訂正」「偽の」「外れた」）・配分   | —                                                                                                                      |
| open Issue                                                                                    | 既に起票済みの候補（重複起票を避ける）                   | —                                                                                                                      |

#### 起票の着手条件

**実害の実例を 1 つ以上、辿れる形で挙げる** — Issue 番号・コミット・archive メモの節のどれか。実害は次の 4 種: **調査を止めた・誤った結論を書かせた・測定をやり直させた・作業の手戻りを生んだ**（長いセッションでの計画精度の低下、同じ訂正の繰り返しは 4 種目）。**挙げられない候補は起票しない**（見送りとして理由つきで記録に残す）。「起きそうだ」「整っていない」は実害ではない。**本文自身が「主因は別」と留保している実例は弱い**。

**この条件は見直し以外でハーネス Issue を起こすときにも当てはまる**（見直しはその条件をまとめて当てる場）。

#### 置き場所の選び方

**散文の規則は破られやすい**（同じセッションのサブエージェントが、定めた直後の規則を破ることがある）。**機械で止められるものは機械へ寄せ、残りを手順・観点・メモリへ**置く。

| 置き場所                              | 向くもの                                                             | 既にある例                                                      |
| ------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------- |
| hook（§5.7）                          | ツール呼び出しの形だけで判定できる禁止事項・毎セッション届けたい情報 | `main` 上の編集・commit の拒否、未完了タスクの注入              |
| CI・テスト・lint                      | コード・設定の**形**で判定できる整合                                 | CI の lint / format / 型 / テスト / ビルド                      |
| agent の評価観点（`.claude/agents/`） | 判断は要るが PR 前に独立に見られるもの                               | evaluator の軸 6「伝播の一貫性」・docs-check の「旧語彙の残存」 |
| skill の手順（§5.3）                  | 決まった時点で必ずやる手順                                           | `finish-task` の Issue close の安全網                           |
| rule（§5.4）                          | 特定のファイルを編集する瞬間に思い出すべき要点                       | `testing.md`・`docs-upkeep.md` の各項目                         |
| docs の規約                           | 上のどれかの正本・流れの区切り                                       | [testing/policy.md](testing/policy.md) §8 の型                  |
| メモリのまま                          | 機械化できない判断の癖                                               | 「主張が証拠を超える」の型                                      |

#### ユーザー判断と偏重の歯止め

候補表（候補 / 実害の実例 / 置き場所 / 採否案と理由）を示し、**起票する本数・起票順（= 優先順）・本業の作業より先に片付けるか後か**をユーザーに仰ぐ（**【通知】** §5.8）。**候補表には窓内の配分を併記する**: archive 行を**ハーネス系**（`scripts/`・`.claude/`・運用 docs だけを対象にしたタスク）と**本業系**（プロキシ本体のコードの変更・観測を対象にしたタスク）に分けた件数と、窓内のコミット数。数値の上限は設けない — 判断はユーザーに渡し、判断に要る数字だけを必ず並べる。起票した各 Issue の本文冒頭には「どの見直しで起票した何本の何本目か・起票順 = 優先順」の位置づけを置き、以後は通常フロー（§5）で 1 本ずつ進める。

#### メモリ整理の基準

整理の対象は**主機のメモリ**に限る（メモリはマシンごとに別で同期していない。記録にマシン名を書く。他の機はその機で回したときだけ）。**件数は `MEMORY.md` を数えない**。

| 基準                                  | 処置                                                                                                                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (a) 機械検査・docs に正本ができた記述 | 手順の複製を削り、「正本は X。ここに写さない」のポインタへ縮める（**Why** と、機械化されずに残った部分は残す）。**ポインタ先が `origin/main` に存在してから**（PR が差し戻されるとどちらにも残らない） |
| (b) 状態が終わった `project` メモリ   | 削除するか、続きのあるメモリへ畳む                                                                                                                                                                     |
| (c) 同じ事を言う複数のメモリ          | 1 つへ統合し、`[[name]]` のリンクを張り替える                                                                                                                                                          |
| (d) 索引                              | `MEMORY.md` の行を実ファイルに合わせる（1 ファイル 1 行）                                                                                                                                              |
| (e) 記録                              | **前後のファイル数と、削除・統合・縮めたファイル名**を記録ファイルの当該節に書く（extract を伴わない整理なら、日付だけの節を先頭に作る）                                                               |

**順序: 候補表をユーザーに確認 → (e) の行を記録ファイルに書いてコミット → メモリを変更 → 前後の件数を確かめて記録を仕上げる。** メモリは git 管理外で戻せず、repo の hook も効かないので、**確認は手順（`AskUserQuestion`）だけが頼り**（**【通知】** §5.8）。記録を先にコミットするのは、記録の PR が差し戻されても消した名前がブランチに残るようにするため。

#### やらないこと

- 起票した Issue の実装（通常フローで 1 本ずつ）。
- テンプレート（[claude-templates](https://github.com/f8924919/claude-templates)）への逆輸入（別手順。見直しで生まれた規則をテンプレートへ運ぶかは、逆輸入のときに判断する）。
- 記録の穴を推測で埋めること。記録が無いものは「記録なし」と書き、要約するときも言い換えない。
