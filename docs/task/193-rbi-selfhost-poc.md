# #193 調査スパイク: RBI ハイブリッド段階導入の自前ホスト PoC（Kasm / Neko・IME キル基準）

## 概要

#72 の採用判断（ハイブリッド段階導入）を受け、本番想定形態である自前ホスト（Kasm Workspaces Community / Neko）で RBI 経路の PoC を行う。

## フェーズ（Issue の受け入れ条件に対応）

1. **IME キル基準**: Kasm / Neko を最小構成で起動し、日本語 IME 入力の忠実度を手動評価。no-go なら以降を打ち切り。
2. **資源実測**: go の方式で同時 10 セッション規模の帯域・RAM・CPU を実測し #72 試算と突き合わせ。
3. **振り分けロジック**: `shouldUseBrowser` / `shouldPromoteToBrowser` を再利用した RBI フォールバック判定の設計案（モック接続まで）。

成果物は PoC 結果と「本採用に進むか / 対象サイト範囲 / 必要インフラ」の判断材料（比較表つき）を本メモへ記録する。

## フェーズ1 実施計画（2026-07-05 ユーザー確認済み）

Issue の受け入れ条件「日本語 IME 入力の忠実度を対象サイトで手動評価し実用品質の go/no-go を記録」を、判定根拠を第三者が追跡できるよう以下に具体化した（criteria-review の指摘を反映）。

### 評価環境

- 開発機（Windows 11 / 32 論理コア / 64GB RAM / Docker Desktop + WSL2）での検証を**一次判定として採用**する。IME パススルーの成立可否は環境差の影響が小さいとの判断。本番想定（Linux サーバー）との差異（レイテンシ特性等）はあり得る旨を結果に注記し、フェーズ2以降で必要なら追試する。
- クライアント: Windows 側ブラウザ + Microsoft IME。
- 環境を汚さない構成: Neko は Docker Desktop 上の compose のみ（終了後にコンテナ・イメージ削除）。Kasm はインストーラがサービスを常駐させるため **PoC 専用の使い捨て WSL ディストリビューション**に導入し、終了後 `wsl --unregister` で丸ごと破棄する。

### 対象サイトと入力シナリオ

- 対象サイト: **Google 検索**（最も一般的な日本語入力シーン。逐次変換・候補選択・サジェストとの干渉を評価できる）。
- シナリオ: 検索ボックスへの ①短い複合語の変換・候補選択・確定 ②長文（ひらがな 20 文字以上）の一括変換 ③変換キャンセル・再変換 ④確定後の追記、を各 10 フレーズ実施。

### go/no-go 判定基準（定性チェックリスト）

以下を Kasm / Neko それぞれで評価し、**1 つでも NG なら当該方式は no-go**:

1. 変換候補ウィンドウが表示され、候補の選択操作ができる
2. 候補ウィンドウの表示位置が入力カーソル近傍にある（入力文字列と重なって読めない等がない）
3. 10 フレーズ入力して文字の取りこぼし・文字化け・二重入力がゼロ
4. 体感遅延が実用を妨げない（入力のたびにストレスを感じる遅延がない）

- **片方のみ go の場合は go の方式でフェーズ2 へ進む**。両方 no-go の場合のみ理由を記録して以降のフェーズを打ち切る。
- 証跡として各方式の評価時のスクリーンショット（可能なら画面録画）を残す。

#### フェーズ1 結論（2026-07-05）

- **両方式とも go**。フェーズ2（資源実測）へ進む。
- 共通の劣化点: IME 候補ウィンドウの表示位置がカーソルから乖離する（両方式とも判読・操作は可能で実用範囲）。本採用時の UX 留意点として記録。
- 差分: Kasm は「IME 入力モード」の明示的なオン操作が必要（= IME パススルーが公式機能として存在）。Neko は特別な操作なしで入力可能だった。
- 本評価は開発機（Windows + Docker Desktop / WSL2）での一次判定。本番想定（Linux サーバー）とはレイテンシ特性が異なり得る。

- 環境構築時の注意（記録）: ①Kasm インストーラが Windows PATH 経由の Docker Desktop バイナリを誤検出して失敗するため、ディストリ内に docker.io / docker-compose-v2 を先に導入してから実行する ②WSL は接続プロセスがなくなるとディストリを自動停止するため、評価中は keepalive プロセスが必要 ③既定インストールにはワークスペース（ブラウザ等）が一切含まれず、管理者が Workspace Registry から追加する必要がある（Chrome イメージ約 2GB を追加取得）。

## フェーズ2 実施計画（2026-07-05 ユーザー確認済み）

Issue の受け入れ条件「go の方式で、対象 1〜数サイト・同時 10 セッション規模の帯域（Mbps/セッション）・RAM・CPU を実測し、#72 の試算（2 CPU / 約 2.7GB / 5〜20Mbps per セッション）と突き合わせる」を以下に具体化した。

### 対象方式とセッション数

- フェーズ1 で両方式 go のため、**Neko と Kasm の両方**を実測して比較表を作る。
- **Neko**: 「1 コンテナ = 1 ブラウザ」構成のため、コンテナ 10 個（= 10 セッション）でフル実測。
- **Kasm**: Community Edition のライセンス制限（同時 5 セッション、#72 §2）のため **5 セッションで実測し、セッション単位の値から 10 セッション規模へ線形外挿**する。外挿である旨を結果に明記する。

### 負荷プロファイル（2 本立て）

| プロファイル | 内容                                               | 位置づけ                                                          |
| ------------ | -------------------------------------------------- | ----------------------------------------------------------------- |
| A: 静的閲覧  | Wikipedia 日本語版の記事を開き、周期的にスクロール | 帯域の下限側（画面変化が間欠的）                                  |
| B: 動画再生  | YouTube で動画を連続再生                           | 帯域の上限側（全画面が常時変化。#72 試算 5〜20Mbps の上限と比較） |

各プロファイルとも定常状態で 3 分間計測する。

### 負荷生成と計測の方法（自動化）

- **クライアント**: Playwright（ヘッドレス Chromium）でセッション数ぶんの WebRTC クライアントを接続し、ログイン → 操作権取得 → リモートブラウザの操作（URL 入力・スクロール・再生開始）まで自動化する。スクリプトは PoC 用のためリポジトリ外（scratchpad）に置き、方法論のみ本メモに記録する。
- **計測**: `docker stats` を 5 秒間隔でサンプリングし CPU% / RAM を収集。帯域は各コンテナの NetIO 累積値の差分から Mbps/セッションを算出。Neko は Docker Desktop 側、Kasm は kasm-poc ディストリ内で同じ方法を用いる。
- **突き合わせ**: セッションあたり CPU コア / RAM GB / Mbps を #72 試算（2 CPU / 約 2.7GB / 5〜20Mbps）と比較し、乖離があれば要因を考察する。

### 計測上の注意（記録すること）

- クライアント（Playwright ×N）とサーバーが同一マシンに同居するため、CPU 実測はサーバー側コンテナの `docker stats` 値のみを採用し、クライアント負荷は含めない。
- 帯域はループバック経由（回線制約なし）。本番のインターネット経由とは輻輳特性が異なる旨を注記する。
- 開発機（Windows + Docker Desktop / WSL2）での一次実測である旨を注記する（フェーズ1 と同じ扱い）。

### フェーズ2 計測結果（2026-07-05）

計測条件: 定常状態 180 秒・5 秒間隔サンプリング。Neko は 10 コンテナ（= 10 セッション）フル実測、Kasm は 5 セッション実測（ライセンス制限）。クライアントは Playwright ヘッドレス Chromium で全セッション自動接続・自動操作。

#### セッションあたりの実測値

| 方式 × プロファイル | CPU（コア） | RAM     | 帯域（送信） |
| ------------------- | ----------- | ------- | ------------ |
| Neko × A: 静的閲覧  | 0.27        | 447 MiB | 2.08 Mbps    |
| Neko × B: 動画再生  | 0.86        | 517 MiB | 2.22 Mbps    |
| Kasm × A: 静的閲覧  | 0.02        | 710 MiB | 0.22 Mbps    |
| Kasm × B: 動画再生  | 0.77        | 907 MiB | 2.91 Mbps    |

#### 同時 10 セッション規模の換算（Kasm は 5 実測 → 10 線形外挿）

| 方式 × プロファイル | CPU 合計 | RAM 合計 | 帯域合計  | 備考 |
| ------------------- | -------- | -------- | --------- | ---- |
| Neko × A            | 2.7 コア | 4.4 GiB  | 20.8 Mbps | 実測 |
| Neko × B            | 8.6 コア | 5.0 GiB  | 22.2 Mbps | 実測 |
| Kasm × A            | 0.2 コア | 6.9 GiB  | 2.2 Mbps  | 外挿 |
| Kasm × B            | 7.7 コア | 8.9 GiB  | 29.1 Mbps | 外挿 |

- Kasm は上記に加えて共通インフラ（api / db / guac / proxy 等 8 コンテナ）の固定費 **約 1.6 GiB RAM**、負荷時に proxy が CPU 数%。

#### #72 試算（2 CPU / 約 2.7GB / 5〜20Mbps per セッション）との突き合わせ

- **全項目で試算より大幅に軽い**。CPU は試算 2 コアに対し実測 0.02〜0.86 コア、RAM は試算 2.7GB に対し 0.45〜0.9GB、帯域は試算 5〜20Mbps に対し 0.2〜2.9Mbps。
- 試算との乖離の主因: ①#72 の Kasm サイジングガイド値は安全側の割当量（実使用量ではない）②Neko は 720p@30 の既定エンコーダ設定でビットレートが約 2.2Mbps に頭打ちし、試算の帯域上限（20Mbps）に遠く及ばない。

#### アーキテクチャ差の発見

- **Neko（WebRTC 常時動画ストリーム）**: 画面内容に関わらず常時エンコード・送信するため、静的閲覧でも帯域約 2.1Mbps・CPU 0.27 コアを消費。帯域はエンコーダ設定で決まり、コンテンツにほぼ依存しない（動画時 2.22Mbps）。
- **Kasm（KasmVNC 差分方式）**: 画面変化がなければほぼゼロコスト（静的閲覧 0.02 コア / 0.22Mbps）。動画など全画面変化時のみ Neko 同等以上のコストになる。**Web プロキシ用途（大半が静的閲覧）では Kasm 方式が資源効率で大きく有利**。
- 画質・fps を上げる設定にすれば両方式とも帯域・CPU は増える。本計測は両方式とも既定設定での値。

#### 計測上の注記

- 開発機（Windows + Docker Desktop / WSL2）での一次実測。クライアントとサーバーが同居するため、サーバー側コンテナの `docker stats` 値のみを採用（クライアント負荷は除外）。帯域はループバック経由で回線制約なし。
- Kasm の 10 セッション値は 5 セッション実測からの線形外挿（Community Edition の同時 5 セッション制限のため）。
- Neko の負荷生成: プロファイル A は Chromium ポリシーで Wikipedia を初期表示＋クライアントから周期スクロール、B は YouTube（Big Buck Bunny）自動再生。Kasm はセッション起動後にリモート Chrome のアドレスバーへ URL を自動入力して誘導（再生はスクリーンショットで確認済み）。

### 後片付け（PoC 終了時）

- Neko: `docker compose down` ＋イメージ削除（フェーズ2 の 10 コンテナ構成も同じ compose プロジェクトで管理し一括削除）。
- Kasm: 専用 WSL ディストリを `wsl --unregister` で破棄。
- `.wslconfig` のメモリ設定（PoC 用に 24GB→40GB へ変更済み）はフェーズ2 完了後に戻す。
- Playwright 等のクライアント側ツールは scratchpad（セッション限りの一時領域）にのみ導入し、リポジトリ・グローバル環境には入れない。
