## 概要

#72 の採用判断（ハイブリッド段階導入）を受け、本番想定形態である自前ホスト（Kasm Workspaces Community / Neko）で RBI 経路の PoC を行う。

## フェーズ（Issue の受け入れ条件に対応）

1. **IME キル基準**: Kasm / Neko を最小構成で起動し、日本語 IME 入力の忠実度を手動評価。no-go なら以降を打ち切り。
2. **資源実測**: go の方式で同時 10 セッション規模の帯域・RAM・CPU を実測し #72 試算と突き合わせ。
3. **振り分けロジック**: `shouldUseBrowser` / `shouldPromoteToBrowser` を再利用した RBI フォールバック判定の設計案（モック接続まで）。

成果物は PoC 結果と「本採用に進むか / 対象サイト範囲 / 必要インフラ」の判断材料（比較表つき）を本メモへ記録する。

## フェーズ1 実施計画（2026-07-05 ユーザー確認済み）

Issue の受け入れ条件「日本語 IME 入力の忠実度を対象サイトで手動評価し実用品質の go/no-go を記録」を、判定根拠を第三者が追跡できるよう以下に具体化した（criteria-review の指摘を反映）。

### 評価環境

- 開発機（Windows 11 / 32 論理コア / 64GB RAM / Docker Desktop + WSL2）での検証を**一次判定として採用**する。IME パススルーの成立可否は環境差の影響が小さいとの判断。本番想定（Linux サーバー）との差異（レイテンシ特性等）はあり得る旨を結果に注記し、フェーズ2以降で必要なら追試する。
- クライアント: Windows 側ブラウザ + Microsoft IME。
- 環境を汚さない構成: Neko は Docker Desktop 上の compose のみ（終了後にコンテナ・イメージ削除）。Kasm はインストーラがサービスを常駐させるため **PoC 専用の使い捨て WSL ディストリビューション**に導入し、終了後 `wsl --unregister` で丸ごと破棄する。

### 対象サイトと入力シナリオ

- 対象サイト: **Google 検索**（最も一般的な日本語入力シーン。逐次変換・候補選択・サジェストとの干渉を評価できる）。
- シナリオ: 検索ボックスへの ①短い複合語の変換・候補選択・確定 ②長文（ひらがな 20 文字以上）の一括変換 ③変換キャンセル・再変換 ④確定後の追記、を各 10 フレーズ実施。

### go/no-go 判定基準（定性チェックリスト）

以下を Kasm / Neko それぞれで評価し、**1 つでも NG なら当該方式は no-go**:

1. 変換候補ウィンドウが表示され、候補の選択操作ができる
2. 候補ウィンドウの表示位置が入力カーソル近傍にある（入力文字列と重なって読めない等がない）
3. 10 フレーズ入力して文字の取りこぼし・文字化け・二重入力がゼロ
4. 体感遅延が実用を妨げない（入力のたびにストレスを感じる遅延がない）

- **片方のみ go の場合は go の方式でフェーズ2 へ進む**。両方 no-go の場合のみ理由を記録して以降のフェーズを打ち切る。
- 証跡として各方式の評価時のスクリーンショット（可能なら画面録画）を残す。

### 後片付け（フェーズ1 終了時）

- Neko: `docker compose down` ＋イメージ削除。
- Kasm: 専用 WSL ディストリを `wsl --unregister` で破棄。
- `.wslconfig` のメモリ設定（PoC 用に 24GB→40GB へ変更済み）はフェーズ2 完了後に戻す。
