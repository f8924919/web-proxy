# テスト方針

[← 目次](index.md)

## 目的

- 機能追加 / 改修時にデグレードを早期検出する
- `docs/spec/` に記述された振る舞いがコードで満たされているかを継続的に確認する
- 等価な評価項目を複数回行う冗長なテストを避け、テスト全体の保守コストを低く保つ

---

## 1. テスト対象スコープ

原則として **ロジック層**（UI / 外部 I/O / エントリーポイントを除く）に限定します。

| 区分                                     | 対象                               |
| ---------------------------------------- | ---------------------------------- |
| 純粋関数・ドメインロジック               | ◯                                  |
| 設定 / 永続化（ファイル I/O）            | ◯（一時ディレクトリで実 I/O 検証） |
| グローバル状態（i18n、設定キャッシュ等） | ◯（フィクスチャで前後復元）        |
| ネットワーク I/O（ローカル完結）         | ◯（§1.1 の条件下のみ・例外的）     |
| 単一 realm での実行環境 smoke            | ◯（§1.2 の条件下のみ・例外的）     |
| UI レイヤ                                | ×                                  |
| 外部ネットワーク I/O                     | ×                                  |
| エントリーポイント                       | ×                                  |

スコープを拡張するときは本ドキュメントと、カバレッジ計測ツールの除外設定を併せて更新してください。

### 1.1 ローカル完結のネットワーク結合テスト

**外部ネットワークへアクセスしない**ことを前提に、テスト内で起動した `node:http` サーバーに対する結合テストを許容します。ファイル I/O を一時ディレクトリで実 I/O 検証するのと同じ考え方で、**モックでは検出できない実行時の非互換を検出する**ことが目的です。

許容条件は以下の 3 つをすべて満たすことです。

1. **接続先の制限**（実際に接続を行うテストが対象）: `127.0.0.1` + `listen(0)` の動的ポートのみ。名前解決を伴うホスト名（`localhost` を含む）を使わない。接続が成立しないテスト（下記「制約」の配線テスト）はこの条件の対象外だが、名前解決は hosts ファイルで完結すること
2. **正当化の要件**: **モックでは原理的に検出できない、ランタイム / 依存の interface 非互換の検出**に限る。振る舞い仕様の検証にこの手段を使わない（振る舞いは純粋関数レイヤで検証する。§2.2 の「下位レイヤでのみ網羅する」原則は維持）
3. **後始末の要件**: `afterAll` でサーバーを閉じ、keep-alive 接続を明示的に破棄する（`server.closeAllConnections()`）。dispatcher / Agent も `close()` する。オープンハンドルでテストプロセスが終了しない状態を作らない

**このカテゴリのテストは原則 1 ファイルに留め、追加するときは本ポリシーの更新を伴う**こととします（レビューを必ず通すため）。

**背景**: `proxyFetch` は SSRF の IP ピン留めのため npm の `undici` から生成した `Agent` を Node 組み込み `fetch()` の `dispatcher` に渡している（[arch/proxy.md](../arch/proxy.md)）。この組み合わせは undici のメジャーバージョン差で実行時にのみ壊れ、型検査でもモックテストでも検出できない。実際に [#236](https://github.com/f8924919/web-proxy/issues/236) で undici 8 系への更新が全経路 502 の回帰を起こし、lint / 型 / テスト / build すべて green のまま `main` に入った。

**制約**: SSRF ガード（`assertSsrfAllowed` の事前検査と `connect.lookup` フック）がループバックアドレスをブロックするため、**`proxyFetch` 自体をローカルサーバーへ接続させることはできない**。テストは「undici の `Agent` を Node 組み込み `fetch` の `dispatcher` として渡せる」という**契約レイヤ**で行う（`tests/lib/proxy/undici-dispatcher.test.ts`）。本番コードにテスト用の seam は入れない（SSRF 設計の攻撃面を広げないため）。

`proxyFetch` の配線が生きていることは、**接続を伴わない**別のテスト（`tests/lib/proxy/proxyFetch.wiring.test.ts`）で確認します。`dns/promises`（事前検査用）だけをモックして事前検査を通過させ、`connect.lookup` フックが実際に呼ばれてループバックを遮断することを cause 連鎖から確認します。このテストは接続が成立しないため上記の許容条件 1 の対象外ですが、名前解決は hosts ファイルで完結し外部ネットワークへは出ません。

### 1.2 単一 realm での実行環境 smoke（`node --test` レーン・#250）

**Jest の実行環境そのものに起因して検証できない事柄**に限り、Jest とは別レーン（`node --test`・`npm run test:realm`）でのテストを許容します。§1.1 とは目的も条件も異なる別カテゴリで、§1.1 の「原則 1 ファイルに留める」ルールの適用対象外です。

**背景**: `jest-environment-node` はテストコードを vm context で実行するため、テスト側で生成したオブジェクトは Node 内部から見て**別 realm**になります。undici の `makeNetworkError` は `isErrorLike(reason)`（`instanceof Error` を見る）が偽のとき `Error` を作り直すため、`connect.lookup` が投げた `SsrfBlockedError` は Jest 上でだけプレーンな `Error` へ置き換わり、`findSsrfCause` の `instanceof` 判定が成立しません（[#237](https://github.com/f8924919/web-proxy/issues/237)）。単一 realm で動く実運用ではこの置換は起きず 403 が返りますが、**その挙動は Jest では原理的に検証できません**。

許容条件は以下の 5 つをすべて満たすことです。

1. **正当化の要件**: **Jest の実行環境（vm realm 分離・モジュールレジストリ）に起因して Jest では原理的に検証できない**ものに限る。単に「Jest で書きにくい」は理由にならない。判定は次の 3 つを示せることとする — (i) `@jest-environment node` を指定しても成立しないこと、(ii) 不可能である機構（vm realm / module registry）を名指しできること、(iii) 根拠となる Issue を引けること
2. **スコープの限定**: **smoke に留める**。振る舞いの網羅は Jest 側（純粋関数レイヤ）で行う（§2.2 の「下位レイヤでのみ網羅する」原則は維持）。このレーンはカバレッジ計測の対象外でもあるため、ここに検証を厚く積まない
3. **外部ネットワークへ出ない**: §1.1 と同じく、名前解決は hosts ファイルで完結し接続も成立させない
4. **本番コードに seam を入れない**: テスト用のフック・エクスポートを本番コードへ足さない。依存の差し替えは `node:module` の `register()` によるモジュールフックで、テスト側だけで完結させる
5. **Jest から隔離する**: ファイルは `tests/realm/` 配下に置き、拡張子は `.mts` とする（`jest.config.ts` の `testMatch` は `tests/**/*.test.ts` なので `.test.ts` で作ると Jest が拾ってしまう）

**§1.1 と同じく、追加するときは本ポリシーの更新を伴う**こととします（件数の上限は設けないが、レーンを増やす判断は必ずレビューを通すため）。

**実行**: `npm run test:realm`。CI では既存の `test` ジョブに step として組み込みます（ジョブ名 `test` は branch protection の必須チェックとして参照される契約のため増やさない。[ci-guide.md](../ci-guide.md) 項目 8）。将来このレーンが Node バージョンマトリクスや OS を必要とし始めたら、[ci-guide.md](../ci-guide.md) 項目 4 に従い「既存の必須チェック名を壊さない別ジョブ」へ切り出します。

**false green を避ける**: このレーンは「検証したい経路を通らないまま緑になる」失敗様式を持ちます。たとえば `dns/promises` のスタブが効かなかった場合、事前検査（`assertSsrfAllowed`）が自分でループバックを弾いて**同じ例外クラス**を投げるため、`connect.lookup` を一度も通らずに緑になります。**スタブが実際に呼ばれたことと、期待する経路を通った証跡（例外 message 中のアドレス等）を必ず assert してください**。テスト件数が 0 でも緑になるのを避けるため、npm script ではテストファイルを**明示指定**します（ディレクトリ指定＋ランナーの既定パターン任せにしない）。

**制約**:

- Node の型ストリップで TypeScript を直接実行するため、対象モジュールが `@/` エイリアスを使っていないこと・`enum` / `namespace` などランタイム機能を持つ TypeScript 構文を含まないことが前提です（`src/lib/proxy/fetch.ts` は Node 組み込みと `undici` のみを import しており条件を満たす）。この結合は prod 側からは見えないため、[arch/proxy.md](../arch/proxy.md) の当該モジュールの節にも明記します
- **このレーンだけ Node 22 以上が要る**。アプリ自体の下限は README「動作環境」のとおり 18 以上（推奨 22）ですが、型ストリップは Node 22.6 以降にしか無いため 18 / 20 では `npm run test:realm` が起動できません（CI は Node 22 で回します）。Node 22 では `--experimental-strip-types` が必要です（22.18+ / 24 では既定有効で、このフラグは将来削除されうる。Node のメジャー更新時に見直してください）
- ルートの `tsconfig.json` は `**/*.ts` しか見ないため、このレーンは `tests/realm/tsconfig.json` で別プロジェクトとして型検査します（`npm run typecheck` が両方を回す）
- カバレッジ計測（`npm test -- --coverage`）の対象外です

**採らなかった代替**: Jest から `child_process` で素の Node スクリプトを起動する案。終了コード越しの検証になり失敗理由が読めず、Node の TypeScript ランナーを素直に使えないため採りません。

## 2. 記述ルール

### 2.1 仕様駆動

- テストは `docs/spec/` に対応する仕様の振る舞いを検証します
- テストファイル / モジュールの先頭コメントに **対応する仕様ファイルへのリンク** を書きます
- テスト関数名は **検証する振る舞いが伝わる形** にします（例: `test_load_returns_defaults_when_file_is_corrupt`）

### 2.2 1 spec = 1 test を原則とする

冗長なテストを避けるため、以下を守ります。

- **同じ振る舞いを複数のテストケースで重ねて検証しない**
- 入力パターンを変えるだけのケースは、利用するテストランナーの **パラメタライズ機構** で 1 関数にまとめる（テスト内で `if` 分岐を増やさない）
- **下位の純粋関数の網羅は下位レイヤのテストでのみ行う**。上位レイヤのテストで間接的に再検証しない

### 2.3 境界でのみ I/O を扱う

- 純粋関数モジュールはモック禁止。入力と出力の比較のみで検証する
- ファイル I/O は **一時ディレクトリ** を使った実 I/O 検証で扱う（テストランナーや言語標準の tmpdir 機能を利用）。モックでファイルシステムを差し替えない
- グローバル状態を変更するテストは fixture / setup-teardown で **前後の値を復元** する

### 2.4 テストの粒度

| 粒度                           | 採用 | 備考                                                                                                                      |
| ------------------------------ | ---- | ------------------------------------------------------------------------------------------------------------------------- |
| 単体テスト（関数・クラス単位） | ◯    | 本ポリシーの基本単位                                                                                                      |
| 結合テスト（モジュール跨ぎ）   | △    | 純粋関数の組み合わせで価値がある場合、ローカル完結のネットワーク結合テスト（§1.1）、単一 realm での実行環境 smoke（§1.2） |
| E2E / UI スモーク              | ×    | 現スコープでは導入しない                                                                                                  |

### 2.5 足した検出器が効くことを確かめる

**不具合を直して回帰テストを足したら、修正を一時的に戻してそのテストが落ちることを確認します。** 落ちなければ、そのテストは対象を見ていません。**通ることの確認だけでは、何も見ていないテストと区別が付きません。**

- **テストに限りません。** lint ルール・静的検査・スモークのステップなど、**「これを足したから今後は検出できる」と言うもの全部**が対象です。
- **書いた時点では正しく見えます。** 「折り返しを検出するつもりの条件が、実は折り返していない状態でも常に落ちる」「最長のケースで一度も走っておらず、対象を狭めても緑のまま通る」といった誤りは、**レビューでは捕まらず、壊して確かめて初めて分かります**。
- **壊す前にコミットします。** 確認のあと `git checkout <file>` で戻すと、**同じファイルの未コミットの作業ごと消えます**。検出器を足した時点でいったんコミットし、**それから壊します**。
- **壊す作業を自動化するなら、追跡下のファイルを書き換えない設計にします。** 対象のコピーを作ってそちらを変異させ、終了後に `cmp` で原本が無傷であることを確かめ、違えば FAIL にします。
- **変異 → red のログは、タスクメモ（`docs/task/<slug>.md`）か PR 本文に貼ります。** 「確認した」という言葉やチャット上の出力は証跡になりません。`evaluator` は貼られていなければ ❌ にします（評価軸 5・§8）。

## 3. ディレクトリ・ファイル構成

```
tests/
├── lib/                  # Jest（既定レーン・npm test）
│   └── proxy/
├── realm/                # node --test（別レーン・npm run test:realm・§1.2）
└── next.config.test.ts   # tests 直下に置く単発のテストもある
```

Jest の `testMatch` は `tests/**/*.test.ts` に加えて `src/**/*.test.ts` も対象にします（`jest.config.ts`）。

**命名規則**

| 種別                | 規則                                                                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| テストファイル      | `{module}.test.ts`（例: `proxy.test.ts`, `url-rewriter.test.ts`）。ただし `tests/realm/`（§1.2）は Jest の `testMatch` に拾われないよう `{module}.test.mts` とする |
| テスト関数          | `{動詞}_{対象}_{条件}`（言語のテスト命名慣習に従う）                                                                                                               |
| パラメタライズの ID | 各ケースを 1 単語で表すラベル                                                                                                                                      |

## 4. 新規仕様 / 改修時のフロー

1. `docs/spec/` を更新する
2. 対応するテストを追加 / 修正する
3. 実装する
4. テストランナーが pass することを確認する
5. カバレッジを確認する
6. 仕様の削除 / 統合時は **対応するテストも併せて削除** する

---

## 5. カバレッジ運用

- **数値閾値は初期は設けません**（計測のみ。CI でも計測・レポート出力のみで fail 条件にしない。[ci-guide.md](../ci-guide.md) 項目 3）
- 数サイクル運用後、実績値からプロジェクト全体・モジュール別に最低ラインを設定します
- 計測対象は **ロジック層（`src/lib` 配下）のモジュール単位** とする（`jest.config.ts` の `collectCoverageFrom`）。UI / エントリーポイント（`src/app` 配下）は対象外。純粋関数と外部 I/O が同居するモジュール（`browserFetch.ts` 等）は関数単位で切り出せないため**丸ごと計測対象に含め**、I/O 分岐による数値低下は許容する（閾値がないため運用上の害はない。テスト済み純粋関数を母集団から隠さないことを優先）
- カバレッジが急に下がった場合、テスト未追加の改修が無いかをレビューで確認します

## 6. テスト対象を広げるとき

UI レイヤ・外部 I/O レイヤまでスコープを広げる場合は、以下を検討してから本ポリシーを更新してください。

| 対象拡張          | 必要なもの                             | 留意点                                                                                                                   |
| ----------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| UI                | 各 UI フレームワーク用のテストハーネス | ヘッドレス環境での実行設定が必要                                                                                         |
| 外部 I/O ラッパー | ネットワークスタブ / モックライブラリ  | **外部**ネットワークは使わない。リクエスト構築の検証はモックで、実行時の非互換の検出はローカル起動サーバー（§1.1）で行う |

拡張時は本ポリシーの 1 章とカバレッジ除外設定を更新してください。

## 7. 実行環境差の検証

自動テストでは再現できない「**開発環境と利用環境の構造的な差**」に起因する不具合への取り決めです。

- **原則**: 権限（昇格 / 非昇格）・OS・ロケール・ネットワーク条件・ディスプレイ有無などの環境差に敏感な機能は、**開発環境での成功をもって完了と判定しない**。利用環境に近い条件を再現した検証をリリース前の完了条件に含める。
- **背景（実運用の事故実績の一般化）**: 開発シェルが管理者昇格済みだったため、特権を要する symlink 作成を内部で行う依存ライブラリの不具合が E2E で全て**偽陰性**となり、リリース後に一般ユーザー環境で初めて露見した例がある。環境差は「テストが通った」の意味を静かに変える。
- **本リポジトリでの主な該当例**: 開発環境（Windows）と運用環境（Linux / コンテナ想定。RBI 併用時は Kasm 等のコンテナ運用）の OS・パス・プロセス管理の差、および外部プロセス（ブラウザコンテナ等）を伴う機能。
- **手段例（Windows・権限差）**: 昇格済みシェルからでも `runas /trustlevel:0x20000 <script.cmd>` で**制限トークン**（Administrators が deny-only・`IsUserAnAdmin()=False`）のプロセスを対話なしで起動でき、非昇格ユーザーの特権エラーを再現できる。実行内容は `.cmd` に書き出し、結果はファイル経由で受け取る（引数の引用符入れ子は壊れやすい）。
- 再現手段が用意できない環境要因が疑われる場合のみ、利用者の実環境での確認を依頼する。

## 8. 観測と原因報告の規律

不具合の調査・検証ハーネスの整備で**同じ形の誤りが繰り返される**ことが分かっています（テンプレート [claude-templates](https://github.com/f8924919/claude-templates) の採用プロジェクトで完了タスク 30 件超を棚卸しした結果、下の 3 型がそれぞれ 6〜12 件）。「慎重に判断せよ」は読んだ側の判断力に依存して繰り返しに効かなかったため、**何を見て、何を出すか**まで固定します。各項目は「見るもの → 出すもの」の 2 欄で書き、**報告に「出すもの」が無ければ項目未達**と判定できるようにしてあります（`evaluator` の評価軸 5、`/start-task` 手順 3.5 がこの表を参照します）。

### 8.1 型 A: 検出器が壊れているのに green（偽 PASS）

テスト・lint・スモーク・判定スクリプトは測定器で、壊れた測定器は red ではなく **PASS** を出します。

| #   | 見るもの                                                                                                         | 出すもの                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | 判定ロジックを足した／変えたら、**対象を壊して red になるか**（§2.5）                                            | 変異 → red のログ（テスト / 変異の出力か、手で壊した時の FAIL 行）。**タスクメモか PR 本文に貼る**（scratchpad に置いたままにしない）。複数の変異を当てるなら、**各変異がどの検査を FAIL させたかの対応**も出す（件数だけでは、変異が別の場所に当たっていても「死亡」と数えてしまう）。**ビルドを伴う変異テストは、ビルドの失敗で fail-closed にする** — 失敗を黙って飛ばすと**直前の変異の成果物がそのまま走り、偽の死因を出す** |
| A2  | 終了コード**だけ**で合否を見ている検査                                                                           | 機械可読な出力行（`PASS: <ラベル>` / `FAIL: <ラベル>` 等）を出し、**行の内容まで照合**していること。2 つの分岐がどちらも同じ exit code に落ちる検査は、片方を完全に壊しても ALL PASS になる                                                                                                                                                                                                                                       |
| A3  | テストの期待値を、**検査対象と同じ理解**で書いていないか（合成データ・自作の見本）                               | **実物**（実際の出力・実際の入力ファイル・実サイトのレスポンスを保存したもの）と突き合わせた結果。実物が無ければ **SKIP と表示**する（黙って飛ばさない）                                                                                                                                                                                                                                                                          |
| A4  | 変異テストが追跡下のファイルを書き換えていないか                                                                 | コピーを変異させる設計であることと、終了後の `cmp` が無傷を示すこと（§2.5）                                                                                                                                                                                                                                                                                                                                                       |
| A5  | 診断メッセージの行き先                                                                                           | 撮れない・読めないときに**黙らない**こと（コマンド置換やパイプのサブシェルに吸われて失敗が見えなくなっていないか）                                                                                                                                                                                                                                                                                                                |
| A7  | **変異テストを回す前に、無変異の複製が green になるか**（対照）                                                  | 対照の結果。**red なら変異を 1 つも回さずに FAIL** にする（複製が変異と無関係な理由で必ず落ちると、どんな変異も「死亡」と報告され、撃墜数がまるごと無意味になる）                                                                                                                                                                                                                                                                 |
| A8  | **検査の対象集合が、意図した集合になっているか**（列挙が静かに欠けていないか）                                   | 対象件数と、**含む側・含まない側の両方**を固定したテスト。**0 件でないこと**も見る（壊れた列挙は「対象なし」で無害に見える）。典型は `git ls-files` による列挙（追跡済みしか返さないので未追跡の新規ファイルが初コミットまで素通りする）                                                                                                                                                                                          |
| A9  | **同じ事実が複数箇所に書かれていないか**（件数・検査名・出力書式・既定値。片方だけ直して隣が残る）               | ツールが権威を持つ事実は**正本 1 か所**に置き、他所からはリンクで参照する。**コードのコメントに実測値を書かない**                                                                                                                                                                                                                                                                                                                 |
| A10 | **測っている間に、測定が使う成果物が変わっていないか**（外で並行して走っているビルド・同じ出力先を使う別の run） | 測定の入口で成果物（実際に起動するバイナリ・ビルド成果物・入力）のハッシュやコミットを記録し、終了時に**変わっていれば症状ではなく前提の不備**として落とすこと。**待機・停止に `pgrep -f` / `pkill -f` を使わない**（パターンを含む自分のシェルにマッチする）                                                                                                                                                                     |

> A6・A11・A12（テンプレート自身の検査ランナー・雛形の木に固有の項目）は本リポジトリでは採用していないため欠番。

### 8.2 型 B: 「観測できない」を「起きていない」と読む

観測手段の側に穴があるのに、対象側の不在として結論する形です（ログの出力先が違う・キャッシュがあると出ない行を待っていた・観測のために付けたオプションが挙動を変えていた、など）。

| #   | 見るもの                                                                                 | 出すもの                                                                                                                                                                                       |
| --- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | 「〜が出ない／起きない」と書こうとしている箇所                                           | **同じ事象を別経路で見た結果**（サーバーログとブラウザの DevTools、出力ファイルと実行時トレース、のように 2 つ目の観測路）。1 経路なら「観測できなかった」と書き、「起きていない」とは書かない |
| B2  | 否定形の主張                                                                             | **独立に実行した run 3 回以上**の一致。run 数を報告に書く                                                                                                                                      |
| B3  | 観測手段が対象に影響しうるか（ブレークポイント・トレース・タイミングを変えるオプション） | 観測手段の有無で結果が変わらないことを確かめた run、または「観測が対象を変えうる」注記                                                                                                         |
| B4  | 「前は出ていたのに出なくなった」                                                         | 比較 2 run の**条件表**（入力・対象のコミット・オプション・環境。本リポジトリでは egress IP・ブラウザティアの有無も）。1 軸でも突き合わせていなければ比較は成立しない                          |

### 8.3 型 C: 3 点が揃う前に原因を宣言する

原因の同定は **(1) コード位置 (2) 判定の構造（何と何を比べてどう分岐したか） (3) 判定対象の実値** の 3 点が揃って初めて言えます。揃う前に宣言して外した例が繰り返されています（古いコミットメッセージの説明を信じて 2 回誤る・条件の違う run を「退行」と読む）。

| #   | 見るもの                                                                                                                                                                                            | 出すもの                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | 「原因は〜」と書く箇所                                                                                                                                                                              | 3 点それぞれの所在（`path:line`／擬似コード／実値）。**1 点でも欠けていれば「仮説」と書く**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| C2  | 過去のコミットメッセージ・タスクメモ・docs に書かれた説明を根拠にする箇所                                                                                                                           | **現在のコードで再確認した結果**（説明は書かれた時点の理解であり、その後の変更で成立しなくなっていることがある）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| C3  | 分岐表・場合分け（「A なら X、B なら Y」）を作った後で、道具（ビルド・入力・スクリプト）の前提が変わった                                                                                            | **表を引き直した**こと（古い表に新しい観測を当てると、存在しない分岐に入れて誤る）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| C4  | 決定実験（判定対象だけを変えて症状が消える／現れる）ができるか                                                                                                                                      | 実験の結果。できない場合はその理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| C5  | 測定のたびの記録                                                                                                                                                                                    | ログ先頭のメタ行（対象のコミットハッシュ・入力・主要オプション）。**メタ行が無いログは比較の根拠に使わない**。**貼るハッシュは「表を書いた時点の HEAD」ではなく「その数値を出した実行の作業ツリー」**（未コミットの変更があればその旨）                                                                                                                                                                                                                                                                                                                                                                                                               |
| C6  | **数・件数・回数**を、受け入れ条件・Issue 本文・タスクメモへ書く箇所。**出所は問わない** — サブエージェントの報告から引く数も、自分が暗算した数も、自分で流したコマンドの出力を読んだ数も同じに扱う | **一次資料（登録簿・index・一覧などの機械出力）を自分で数えたコマンドとその出力**（回数・経緯は数えるのではなく、示された `path:line` を開いて確かめた旨）と、**数えた時点**（コミットハッシュ）。**足した本数からの暗算・記憶・目視で書かない。** 数え方の道具は**1 行に複数ある一致を落とさないもの**を選ぶ（`rg -o` など。**道具の癖は版に依存する**ので、同じパターンで一致数と当たった行数の両方を採り、一致数の方が多いことを確かめてから使う）。**行数と一致数を区別する。** 報告者の視野がそのまま母集団になる事故が繰り返し起きた — 「兄弟 5 本」を調査役が**その 5 本だけ見て**「前提はずれていない」と返し、一次資料を数えたら 16 本だった |

> **C6 の適用範囲**: サブエージェント側では `investigate` に限らず**報告一般**に掛かる。「出所を添える」項目を agent 定義に置いてあるのは [`investigate`](../../.claude/agents/investigate.md) と [`implementer`](../../.claude/agents/implementer.md) の 2 本で、**副産物の数の転記事故は、受け手側であるこの C6 が拾う**。**主エージェント自身が書く数に対応する agent 側の項目は無い**ので、C6 がそのまま唯一の歯止めになる。
>
> **§8.1 A9 との違い**: A9 は**書く場所**の規則（同じ事実を 2 か所に書かない）で、**C6 は書く前の手順**である — **数を書くなら、その数を自分で数えてから書く**。
