# CI 導入ガイド（設計指針）

このリポジトリはまだ CI 設定本体（ワークフローファイル）を持ちません。本ガイドは、CI を導入する際の**設計指針チェックリスト**です（テンプレート [claude-templates](https://github.com/f8924919/claude-templates) から取り込み）。実運用プロジェクトで得た知見を一般化したもので、GitHub Actions を例に書いていますが考え方は他の CI サービスでも同じです。

## チェックリスト

### 1. ローカルの検証ゲートと同じコマンドを回す

CI の lint / フォーマット / 型チェック / テストは、`CLAUDE.md` に記載したローカルコマンドと**同一**にする。CI 専用の別コマンドを作ると、ローカル green ↔ CI red の drift が生まれる。コマンドを変えたら CLAUDE.md と CI を同時に更新する。

### 2. 対象範囲の対称性を保つ

lint / フォーマット / 型チェックの対象を、ソースディレクトリだけでなく **テスト・補助スクリプトにも**そろえる（例: `src/` だけ format チェックして `tests/` `scripts/` が対象外、という非対称を作らない）。範囲が非対称だと、チェック外の領域に品質劣化が静かに溜まる。

### 3. カバレッジは「計測を先に、閾値は後で」

まず CI でカバレッジ計測とレポート出力だけを自動化し、数値閾値（fail 条件）は数サイクル観測してから導入を再検討する。初手で閾値を入れると、実態と合わない数字が開発を止めるか、閾値を下げる運用が常態化する。大型モジュールの計測除外（omit 等）はテスト方針 docs（`docs/testing/policy.md`）と双方向に同期し、段階的に解除する。

### 4. 配布ターゲットの OS でテストする

配布対象 OS がある場合、少なくとも主要ターゲット OS でもテストジョブを回す（OS 固有 API・パス・ソケット仕様のバグは単一 OS の CI をすり抜ける）。追加は**既存の必須チェック名を壊さない別ジョブ**として行い、green の実績を確認してから必須チェックに昇格させる。

### 5. lint / 型チェックの厳格化は段階導入

ルールセット追加・strict 化は「設定変更 + 挙動不変の違反修正」だけで 1 PR にする（機能変更と混ぜない）。誤検知の多いルールは理由をコメントで添えて恒久 ignore にする。費用対効果が合わない厳格化（大量の型注釈後付け等)は見送りの判断も記録する。

### 6. SAST（CodeQL 等）は低コストで導入できる

静的セキュリティ解析はワークフロー追加のみで導入できる。トリガは PR / main への push / 週次スケジュールの組み合わせが標準。必須チェック化は誤検知ノイズの実績を見てから判断する。

### 7. 依存キャッシュを有効化する

セットアップ系アクションのキャッシュ（例: `setup-uv` の `enable-cache`、`actions/setup-node` の `cache`）を有効化する。リリースビルドの OS マトリクスでは特に効果が大きい。見送る場合は理由を記録する（後から「意図的か未着手か」が判別できなくなるため）。

### 8. main 保護と CI を連動させる

branch protection の必須ステータスチェックに CI ジョブを指定し、管理者にも適用する（GitHub なら `enforce_admins`）。クライアント側の hook（[docs/git-workflow.md](git-workflow.md) §1）と合わせて二段構えになる。

### 9. リリース後の実資産スモークを完了条件にする

**本番の外部サービス API・実リリース資産（配布物）に依存する機能**（更新チェック・署名検証・テレメトリ等）を含むリリースは、公開直後に**実資産・本番 API に対する E2E スモーク**を行い、pass を確認してからリリース完了（アナウンス・タスク完了）とする。例: 更新チェック系の変更なら、旧バージョンを偽装した実バイナリで新リリースを検知・処理できることを確認する。

外部 API の契約変更は**防止できない**（開発時 PoC の成功はその時点の契約しか保証しない）ため、この種の機能は「リリースのたびに実資産で検出し、破壊の影響を 1 リリース以内に収める」運用で補う。CI に組み込めない場合は手動チェックリストでもよいが、完了条件であることを docs に明記する。
