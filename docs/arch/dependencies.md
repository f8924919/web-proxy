# 依存パッケージ管理

> 関連: [アーキテクチャ目次](index.md) / [CI 導入ガイド](../ci-guide.md)

npm 依存パッケージのバージョン固定方針と、脆弱性対応の運用を記載します。特に `package.json` の `overrides` は「なぜ固定したか」「いつ外すか」がコードから読み取れないため、本ファイルを正本とします。

## 1. 基本方針

- 直接依存のバージョン更新は **dependabot の PR** に従う。CI（`test` / CodeQL）が green であることを確認してマージする。
- 推移依存の脆弱性は、まず上流パッケージの更新で解消できるかを確認する。解消できない場合に限り `overrides` を使う。
- `npm update` は多数の推移依存を一括で動かすため、脆弱性対応の手段としては使わない（変更範囲が広く、退行時の切り分けが困難になるため）。
- `overrides` は **恒久的な設定ではなく一時的な回避策**として扱う。追加時に必ず「削除条件」を本ファイルに記載する。
- **`npm audit` の件数を目標にしない。** 件数は npm の `fixAvailable` 判定に左右され、より安全な版に上げたほうが件数が増えることがある（§3 参照）。判断は実際に修正済みの勧告数で行う。
- `postcss` の override に伴い `nanoid`（postcss の依存）も 3.3.12 → 3.3.16 に巻き込まれる。意図した副次変更。

## 2. overrides 一覧

`package.json` の `overrides` に定義しているエントリと、その理由・削除条件です（#223）。

| 対象                | 固定バージョン | 固定理由                                                                                                                                                        | 削除条件                                             |
| ------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `postcss`           | `^8.5.23`      | next が `postcss: "8.4.31"` を**完全固定**（`^` なし）しているため、上流更新では昇格しない。8.5.17 以下に XSS・任意ファイル読み取り・パストラバーサルの勧告あり | next が要求する postcss が 8.5.23 以上になったら削除 |
| `sharp`             | `^0.35.3`      | next の optionalDependency `^0.34.3` の範囲外。0.35.0 未満に libvips 由来の CVE 4 件（CVE-2026-33327 / 33328 / 35590 / 35591）あり                              | next が要求する sharp が 0.35.0 以上になったら削除   |
| `brace-expansion@5` | `^5.0.8`       | `minimatch@10` 系（`typescript-eslint` 経由）が 5.0.7 で解決される。5.0.7 以下に OOM クラッシュを伴う DoS 勧告あり                                              | 上流が 5.0.8 以上で解決するようになったら削除        |
| `js-yaml@3`         | `^3.15.0`      | `@istanbuljs/load-nyc-config`（`babel-plugin-istanbul` → jest のカバレッジ経路）が 3.14.2 で解決される。マージキー連鎖による二次計算量 DoS 勧告に該当           | 上流が 3.15.0 以上で解決するようになったら削除       |
| `js-yaml@4`         | `^4.3.0`       | `@eslint/eslintrc` 経由で 4.2.0 が解決される。同上の勧告に該当                                                                                                  | 上流が 4.3.0 以上で解決するようになったら削除        |

### メジャー系列ごとの指定

`brace-expansion` と `js-yaml` は**複数のメジャー系列が同一ツリー内に併存**する。`overrides` のフラットなキー（`"brace-expansion": "^5.0.8"` など）は semver 範囲を無視して**全解決箇所を強制置換**するため、`minimatch@3` が期待する 1.x に 5.x を流し込んで壊す。

これを避けるため、npm のセレクタ構文 `"<name>@<major>"` を用いてメジャー系列ごとに指定する。

```json
"overrides": {
  "brace-expansion@5": "^5.0.8",
  "js-yaml@3": "^3.15.0",
  "js-yaml@4": "^4.3.0"
}
```

## 3. 未解消の脆弱性

| 対象              | 勧告                                           | 残す理由                                                                                                                                                         | 追跡                                            |
| ----------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `brace-expansion` | OOM クラッシュを伴う DoS（脆弱範囲 `<=5.0.7`） | 脆弱範囲が **1.x / 2.x 全体を含む**（1.1.16 も 5.0.7 未満）一方、修正版は 5.0.8 以上のみで 1.x / 2.x へのバックポートが無い。5.x への強制は API 非互換のため不可 | 上流（`minimatch@3` / `minimatch@9`）の更新待ち |

### brace-expansion を 5.x に強制できない理由

v5 は v1 / v2 と **API 非互換**。v1 / v2 は関数を直接 export するが、v5 は `{ expand }` を持つオブジェクトを export する。

```
v1: typeof require('brace-expansion') === 'function'   → require(...)('a{b,c}d') が動く
v5: typeof require('brace-expansion') === 'object'     → 同じ呼び出しは TypeError
```

`minimatch@3`（`@eslint/eslintrc` 経由）・`minimatch@9`（`glob` 経由）はいずれも関数として呼び出すため、フラットな `overrides` で 5.x を強制すると **eslint と jest が実行時に壊れる**。したがってこの 2 ノードは上流が対応するまで残す。

### `npm audit` の件数が実エクスポージャと逆行する点（重要）

`brace-expansion` には勧告が 3 件ある（`<1.1.16` / `>=2.0.0 <2.1.2` / `<=5.0.7`）。1.1.16 / 2.1.2 は**このうち 2 件が修正済み**で、1.1.15 / 2.1.1 より安全である。

しかし `npm audit` の**報告件数は逆に増える**。1.1.15 のときは npm が「昇格すれば直る」と判断して単独の 1 エントリで済むが、1.1.16 まで上げると残る `<=5.0.7` に対する提案が「eslint のメジャー更新」しか無くなり、`fixAvailable` が解決不能と判定されて `minimatch` 以下の依存チェーン全体が展開される。

| lock の解決                | 実際に修正済みの勧告 | `npm audit` high |
| -------------------------- | -------------------- | ---------------- |
| 1.1.15 / 2.1.1             | 0 / 3                | 1                |
| **1.1.16 / 2.1.2（採用）** | **2 / 3**            | **27**           |

本リポジトリは**実エクスポージャを優先**し、クリーン再生成の自然な結果である 1.1.16 / 2.1.2 を採る（#223 で実測のうえ決定）。古い版に固定して件数を小さく見せることはしない。

したがって **`npm audit` の high 27 件は正常な状態**であり、その全件が `brace-expansion` の未修正勧告 1 件を根とする。件数だけを見て判断せず、`npm audit --json` の `vulnerabilities` のキーが `brace-expansion` と `minimatch` およびその依存元のみであることを確認する。**この集合の外に新しいキーが現れたら新規の脆弱性混入を疑う。**

> このノイズにより `npm audit` は件数ベースの監視には使えない。CI に監査を組み込む場合は、件数ではなく検出パッケージ名の集合で判定すること。

### 本リポジトリでの影響範囲

- `postcss.config.*` / `tailwind.config.*` は存在せず、`src` 配下に `next/image` の import もないため、postcss（CSS ビルド経路）・sharp（Image Optimization API）はいずれも実質使われていない。overrides はサプライチェーン衛生が目的。
- **`next/image` を導入する際は `sharp` の override を必ず再評価すること。** next が宣言する範囲（optional `^0.34.3`）の外に固定しているため、Image Optimization を使い始めた時点で next 側のバージョンチェックや ABI 差で失敗し得る。`postcss` も同様に next のピン留めを横取りしているため、CSS ビルド経路を使い始める際は再評価する。

## 3.1 next のバージョン下限

`next` は **15.5.21 以上**を維持すること。15.5.21 未満には SSRF（Server Actions / rewrites）・DoS（App Router / Image Optimization API）・内部 Server Function エンドポイントの漏洩など high 8 件の勧告がある。

この 8 件は当初「stable に修正版が存在しない」と誤判断した。`npm audit` が集約表示する `range` が `9.3.4-canary.0 - 16.3.0-preview.7`（16.x 系まで含むアドバイザリの和集合）だったためだが、**per-advisory のレンジはいずれも `<15.5.21`** で、15.5.21 / 15.5.22 は stable として公開済みだった。集約 `range` を実際の解決状況と取り違えないこと（§4 手順 1）。

## 3.2 undici のバージョン上限（7 系固定・#236）

`undici` は **`^7.29.0`** に固定する。**8 系以降へ上げてはならない。**

`src/lib/proxy/fetch.ts` は SSRF の IP ピン留め（#129）のため npm の `undici` から `Agent` を生成し、**Node 組み込みの `fetch()`** へ per-request の `dispatcher` として渡している。組み込み `fetch()` の実体は Node にバンドルされた undici であり、npm 側とは別インスタンス。undici 8 系では dispatcher のハンドラ interface が刷新され（`onRequestStart` 等）、Node バンドル版と非互換になる。

- 症状: `TypeError: fetch failed` / cause `invalid onRequestStart method`（`UND_ERR_INVALID_ARG`）。**プロキシ中継が全経路で 502 になる**
- Node のバージョンが undici 8 の要求（>= 22.19.0）を満たしていても再現する（Node v24.14.1 で確認）
- 実装上の背景・解除条件は [proxy.md §undici のメジャーバージョン制約（7 系固定・#236）](proxy.md#undici-のメジャーバージョン制約7-系固定236)
- Dependabot は `.github/dependabot.yml` の `ignore` で major 更新を止めている。**`ignore` は security update にも効く**ため、undici の GHSA はリポジトリの Security タブで別途確認する
- undici 8 の CVE 修正を取り込めないことの影響は限定的。実際の HTTP リクエストを処理しているのは Node 組み込みの undici であり、npm 側は `Agent` 生成にしか使われていない

### dependabot の PR を CI green だけで信用しない（#236 の教訓）

§1 の「CI が green であることを確認してマージする」は**必要条件であって十分条件ではない**。#236 では lint / 型 / テスト / build のすべてが green のまま、プロキシ中継を全滅させる回帰が `main` に入った。

**ランタイムの実装（Node 組み込みの undici、Playwright のブラウザバイナリなど）と npm パッケージの版が噛み合う必要がある依存**は、型検査にもモックテストにも現れない形で壊れる。`undici` / `playwright` のメジャー更新 PR では、CI に加えて `npm run dev` での実挙動確認を行う。回帰検知テストは [testing/policy.md §1.1](../testing/policy.md) を参照。

## 4. 変更手順

1. `npm audit --json` で各脆弱性の `nodes`（実際の解決パス）と per-advisory の脆弱範囲を確認する。npm が集約表示する `range` はアドバイザリの和集合で実態とずれるため、`via` の個別レンジを見る。
2. `node -e "require('./<path>/package.json').version"` で各解決箇所の**実インストール版**を確認する（`npm ls` の表示は wanted 版を含むため読み違えやすい）。
3. `overrides` を追加し、`package-lock.json` を再生成する。
4. `npm ls <name> --all` で全解決箇所が修正版になったことを確認する。
5. `npm audit` の high / total 件数を追加前と比較する。**減るとは限らない**（修正版が存在しないパッケージを固定すると、npm が依存チェーン全体を修正不能と判定して件数が増える）。
6. 該当パッケージのメジャー跨ぎ更新になる場合は、`require()` した際の export 形状が互換かを実際に確認する。
7. 本ファイルの表を更新する。
