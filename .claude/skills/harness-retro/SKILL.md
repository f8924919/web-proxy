# harness-retro — ハーネス見直しとメモリ整理

[docs/git-workflow.md](../../../docs/git-workflow.md) §5.9 を回すオーケストレーション skill。**窓・情報源・起票の着手条件・置き場所・偏重の歯止め・メモリ整理の基準の正本は §5.9**。この skill は手順と抜き出しのコマンドに徹し、ルールを再定義しない。回ごとの記録は [docs/harness-retro-log.md](../../../docs/harness-retro-log.md)。

> **ホスト操作の読み替え**: Issue 起票・PR は GitHub の `gh` 前提。GitHub 以外は git-workflow.md 冒頭注記に従う。

## 前提

- **ユーザーが求めたときだけ回す**（§5.9「いつ回すか」）。引数が無ければどちらの段階かをユーザーに確かめる。
- メモリの場所は、ハーネスがシステムプロンプトで渡すものを使う（パスをこの skill に書かない）。
- `main` で直接作業しない。記録のコミットは `docs/harness-retro-<YYYY-MM-DD>`（extract）/ `docs/memory-cleanup-<YYYY-MM-DD>`（cleanup）のブランチで行う（§4）。

## extract — 候補の抽出と起票

1. **窓を決める**（§5.9「窓」）: `git fetch origin` の後、始点 = 記録ファイルで「窓:」の行を持つ節のうち、いちばん上の節の終点コミット（メモリ整理だけの節は窓を持たないので数えない）、終点 = `origin/main` の HEAD。**始点のコミット自身の変更は窓に入らない**（`START..END` は始点を含まない）ので、あるタスクを窓に含めたいときは、そのマージコミットではなくその直前のコミットを始点にする。初回（「窓:」の行を持つ節が無い）は始点をユーザーと決める（プロジェクト立ち上げのコミットなど）。
2. **情報源を抜き出す**（§5.9「情報源と、形が揃っていないこと」。リポジトリのルートで実行する）:

   ```bash
   START=<前回の終点コミット>; END=$(git rev-parse --short origin/main); F=docs/task/archive/index.md
   rows() { git show "$1:$F" | sed -n 's/^| \[\([^]]*\.md\)\](.*/\1/p' | sort -u; }
   # (1) 窓内の archive 行 — ファイル名で比べる（完了日の列・git diff の + 行では切らない）
   comm -13 <(rows "$START") <(rows "$END")
   # (2) 各行の全文（要判断・follow-up 候補・経緯）と、メモに訂正ログ表があればそのデータ行（ヘッダ 2 行を除く）
   for f in $(comm -13 <(rows "$START") <(rows "$END")); do
     echo "== $f"
     git show "$END:$F" | command grep -F "| [$f]("
     git show "$END:docs/task/archive/$f" | awk '/^## 訂正ログ/{p=1;next} /^## /{p=0} p && /^\|/' | tail -n +3
   done
   # (2b) 「完了タスクの経緯・申し送り」節に窓内で足された行（表の行にリンクを持たない申し送りを拾う）
   sec() { git show "$1:$F" | awk '/^## 完了タスクの経緯・申し送り/{p=1;next} /^## /{p=0} p'; }
   echo "== (2b) 経緯・申し送り節に窓内で足された行"
   diff <(sec "$START") <(sec "$END") | sed -n 's/^> //p'
   # (3) 訂正コミットと、窓内のコミット数
   echo "== (3) 訂正コミット / 窓内のコミット数"
   git log --no-merges --format='%h %ad %s' --date=short "$START..$END" | command grep -E '訂正|偽の|外れた'
   git rev-list --count --no-merges "$START..$END"
   # (4) open Issue（重複起票を避ける）
   echo "== (4) open Issue"
   gh issue list --state open --limit 200 --json number,title -q '.[] | "#\(.number) \(.title)"'
   ```

   `grep` は `command grep` で呼ぶ（対話シェルでは `grep` が関数やエイリアスで別の実装に置き換わっていることがあり、ignore 規則などで結果が変わる）。(2) の grep は表の行の形（`| [<ファイル名>](`）で当てる — `[<ファイル名>]` だけだと「完了タスクの経緯・申し送り」節で同じメモへリンクする段落にも当たり、(2b) と同じ段落が 2 回出て「段落が 2 つある」と誤読しやすい。(2b)〜(4) の先頭の `== (…)` の行は、直前のファイルの出力と続けて読まないための区切り。メモリは窓を掛けずに全ファイルを読む。**窓内の archive 行は (2) で出した全文を読む**（概要だけで済ませない）。`## 訂正ログ` を持たないメモは本文を読む。

3. **候補表を作る**: 候補（繰り返した失敗の型） / 実害の実例（辿れる形。窓の外でもよい） / 置き場所（§5.9 の表から） / 採否案と理由。**実害の実例が挙げられない候補は採否案を「見送り」にする**（§5.9「起票の着手条件」）。配分（archive 行のハーネス系 / 本業系の件数と、窓内のコミット数）を併記する。
4. **ユーザーに仰ぐ**: 候補表と配分をチャットに全文で示し、起票する本数・起票順（= 優先順）・本業の作業より先か後かを `AskUserQuestion` で決める。**【通知】** [git-workflow.md](../../../docs/git-workflow.md) §5.8。
5. **起票する**: 採用した候補を §3 のテンプレで 1 本ずつ起票する（`gh issue create` は都度確認。§5.3）。本文冒頭に位置づけ（この見直しで起票した N 本の何本目か・起票順 = 優先順・ユーザー判断）を置く。
6. **記録する**: `docs/harness-retro-<YYYY-MM-DD>` ブランチで、記録ファイルの先頭に節を足す（雛形はファイル内のコメント。次回の始点になるので「窓:」の行を必ず書く）。見送った候補も理由つきで残す。起票した Issue を `docs/task/index.md` の「起票済み・未着手の Issue」表へ載せ、同じ PR にする。**記録にメモリの本文を写さない**（ファイル名だけ）。
7. PR を作る。**【通知】** マージ待ち（§5 step 8）。以後の各 Issue は `/start-task` から 1 本ずつ。

## cleanup — メモリ整理

1. **対象を確かめる**: 主機のメモリか（§5.9「メモリ整理の基準」。他の機はその機で回す）。件数は `MEMORY.md` を除いて数える:

   ```bash
   M=<メモリの場所>
   LIST=$(for f in "$M"/*.md; do
     [ "$(basename "$f")" = MEMORY.md ] && continue
     printf '%s\t%s\n' "$(basename "$f")" "$(sed -n 's/^ *type: *//p' "$f" | head -1)"
   done)
   printf '%s\n' "$LIST"; printf '%s\n' "$LIST" | command grep -c .
   ```

   一覧と件数を `tee /dev/stderr | wc -l` で同時に出さない。標準出力と標準エラーを同じファイルへ流すと（`> out.txt 2>&1`。記録に貼る出力を取るときの形）、`tee` が `/dev/stderr` を開き直した時点でファイルが切り詰められ、それまでの出力が消えたり件数で上書きされたりする（端末に出すだけなら起きない）。

2. **候補表を作る**: ファイル名 / 該当する基準 (a)〜(d) / 提案する処置 / (a) ならポインタ先。**(a) のポインタ先は `origin/main` に存在するものだけ**（`git fetch origin && git cat-file -e origin/main:<path>`）。無いものは候補から外して理由を書く。**機械化されていない判断の癖（「一定時間ハーネス側に寄ったら報告して本業へ戻る提案をする」のような）は縮めない**。
3. **ユーザーに確認する**: 候補表をチャットに全文で示し、処置ごとに `AskUserQuestion` で可否を取る。**【通知】** [git-workflow.md](../../../docs/git-workflow.md) §5.8。メモリは git 管理外で戻せず、repo の hook も効かない — 確認はこの手順だけが頼り。
4. **記録を先にコミットする**: `docs/memory-cleanup-<YYYY-MM-DD>` ブランチで、記録ファイルの該当する回の節（extract を伴わない整理で該当する回が無ければ、`## YYYY-MM-DD（メモリ整理のみ）` の節を先頭に作る）に「メモリ整理（日付・マシン名）: 前 N → 後（予定）M。削除: … / 統合: … / 縮めた: …」を書いてコミットする。
5. **メモリを変更する**: 承認された処置だけを行い、`[[name]]` のリンクと `MEMORY.md` の索引を合わせる。
6. **仕上げる**: 手順 1 のコマンドで後の件数を数え直し、記録の「（予定）」を実測に置き換えてコミットする。PR を作る。**【通知】** マージ待ち（§5 step 8）。

## やらないこと

- 起票した Issue の実装（通常フローで 1 本ずつ）。
- 実害の実例が無い候補の起票、配分を示さずに起票本数を決めること。
- テンプレート（[claude-templates](https://github.com/f8924919/claude-templates)）への逆輸入（別手順。見直しで生まれた規則を雛形へ運ぶかは、逆輸入のときに判断する）。
- 承認前のメモリの削除・統合、記録をコミットする前のメモリの変更。
- 記録の穴を推測で埋めること（「記録なし」と書く）。
