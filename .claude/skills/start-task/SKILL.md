# start-task — タスク立ち上げ（ワークフロー前半）

[docs/git-workflow.md](../../../docs/git-workflow.md) §5 step 1〜6 を定型化するオーケストレーション skill。`verify-gate`（step 7）・`finish-task`（step 9）と対になる前半の入口。
**ルール（Issue テンプレ・ブランチ命名・更新先など）の正本は git-workflow §3/§4/§5**。この skill は順序と入口に徹し、ルールを再定義しない。

> **ホスト操作の読み替え**: 本 skill は GitHub の `gh`（Issue 起票）を前提に書いている。GitHub 以外のホストでは git-workflow.md 冒頭注記に従い当該ホストのコマンド／用語へ読み替える。Issue ベース開発を採用しない（ホスト無し含む）場合は、Issue の代わりに `docs/task/<slug>.md` を受け入れ条件の正本として用いる。branch 作成・investigate・docs 先/テスト先ゲートはホスト非依存でそのまま機能する。

## この skill の最重要目的：順序の強制

**docs 先・テストファースト**を順序ゲートとして強制する。実装を docs/テストより先に進めない。step 4・5 を飛ばして step 6 に進まないこと。

## 手順

1. **Issue 確認 / 起票**（§3）
   - 対象 Issue があれば内容（背景・受け入れ条件・対象範囲）を確認する。
   - 無ければ §3 テンプレ（背景/目的・受け入れ条件・対象ファイル・関連 docs リンク）で起票する。受け入れ条件の中身はユーザーと確認しながら決める（勝手に確定しない）。
   - Issue を使わない運用では、同じ項目を `docs/task/<slug>.md` に記述してこれを正本とする。

2. **`main` 最新化＋ブランチ作成**（§4）
   - `git checkout main && git pull --ff-only origin main`
   - §4 の命名規則でブランチを作成する（Issue を伴う作業は `feature/<issue>-<desc>` / `bugfix/...` / `hotfix/...`、伴わない作業は `refactor/` `docs/` `chore/`）。

3. **調査（`investigate` 起動）**（step 3）
   - `investigate` サブエージェントを起動し、docs 先・コード裏取りの結論（要点・関連 `path:line`・裏取りメモ）だけを受け取る。
   - **設計・実装方針の判断は委譲しない**。investigate は判断材料の収集のみ。

3.5. **受け入れ条件レビュー（`criteria-review` 起動）**（step 3.5）

- `investigate` の結論を踏まえ、`criteria-review` サブエージェントを起動して受け入れ条件・spec **そのものの妥当性**（テスト可能・網羅的・非曖昧・意図との整合）を点検し、指摘・改善案を受け取る。安価（Sonnet）な常時運用の助言。
- **助言でありゲートではない**。指摘の採否・受け入れ条件の修正可否は主エージェント＋ユーザーが判断する（§5.1）。`evaluator`（step 7・実装の適合性を PR 前に評価）とは対象が逆である点に注意。
- `refactor` / `docs` / `chore`（受け入れ条件を持たない作業）では省略してよい。条件を修正した場合は Issue（または `docs/task/<slug>.md`）へ反映してから先へ進む。

4. **【確認ゲート】docs 先行**（step 4）
   - 設計を `docs/spec/` / `docs/arch/` に**先に**反映する（[docs-guide.md](../../../docs/docs-guide.md) §4 の更新先に従う）。
   - **これは判断であり skill は自動化しない**。設計内容は主エージェントが立案し、設計上の選択・トレードオフはユーザーに確認する（§5.1）。skill の役割は「実装より先に docs を固める」順序を守らせること。

4.5. **設計レビュー（`design-review` 起動・条件付き）**（step 4.5）

- **発火可否は主観で決めない**。設計レビューモード（§5.2）と investigate（step 3）の「設計レビュー推奨」で判定する。モードが `auto` で推奨が `yes`（§5.5 トリガ該当）、または `always` のとき、docs に固めた設計案を `design-review` サブエージェント（Opus）で点検し、指摘・改善案を受け取る。
- **助言でありゲートではない**。設計方針の最終決定は主エージェント＋ユーザー（§5.1）。推奨が `yes` のとき主エージェントは自己判断でスキップせず、省略する場合は**理由をユーザーに提示して承認を得る**。ユーザーはオン / オフ両方向でオーバーライドできる。
- モードが `off`、または推奨が `no`（トリガ非該当）なら省略してよい。`criteria-review`（step 3.5・条件の妥当性）とは対象が異なり、設計案そのものを見る。

5. **【確認ゲート】テスト先行**（step 5）
   - 受け入れ条件・spec に基づいてテストを**先に**書く（実装に合わせて書かない。[テスト方針](../../../docs/testing/policy.md)）。
   - **テスト内容の決定は判断であり skill は自動化しない**。何を検証するかは主エージェント＋ユーザーが決める。skill は「実装より先にテストを書く」順序を守らせること。

6. **実装 → green**（step 6）
   - 実装してテストを green にする。red 単独ではコミットせず、green にしてから 1 コミットにまとめる（§5.1）。

> ここから先（PR 前の検証ゲート）は `/verify-gate`、マージ後は `/finish-task` に引き継ぐ。

## やらないこと

- **docs 設計・テスト内容の自動生成／判断の肩代わり**。step 4・5 は確認ゲートに留め、中身は主エージェント＋ユーザーが決める（§5.1/§5.2）。
- ルール（Issue テンプレ・ブランチ命名・更新先）の再定義。正本は git-workflow §3/§4/§5。
- 順序の省略。docs/テストを飛ばして実装に進まない。
- 設計外の問題の独断対応。出たらユーザーに対応案を提示して確認する（§5.1）。
